# 实际音频驱动时间轴与封装边界优化方案

> 状态：待用户审阅，尚未实施。
> 本文仅记录优化方案。代码、配置、模板及测试执行须等待用户后续指令。

## 一、目标与边界

核心原则：**确认后的解说内容是约束，Analysis 预估时长不是约束；最终制作时长由真实配音、素材及明确的画面编排决定。**

本次建议保留现有两阶段接口、文本确认机制和原子交付机制，在现有 Render 执行链内完成以下优化：

1. 阻断 Analysis 预估时长参与 Render 帧数计算。
2. 根据真实音频和素材建立确定性的内容时间轴。
3. 区分内容结束位置与最终视频覆盖帧数。
4. 完整混音超尾时，固定混音并有界调整画面，而不是裁声音或原样重试。
5. 将正常时间轴调整与普通失败修复分开记账。

不建设通用剪辑引擎，不修改已确认原稿，不重新生成已经有效的配音，也不默认登录服务器或执行部署。

## 二、问题定位

### 2.1 本次第 18 镜的已报告现象

| 项目 | 已报告数值 |
| --- | --- |
| 豆包配音实际时长 | 10.872 秒 |
| Render 视频时长 | 327 帧 / 30fps = 10.900 秒 |
| 完整混音时长 | 10.900333 秒 |
| 超出部分 | 48kHz 下约 16 个采样点，约 0.33 毫秒，尾部非纯静音 |

这些数值作为回归样本，实施时仍需读取对应原始音频及 PCM 样本数核实，不能仅依赖小数时长字符串。

从这些数值看，配音本身已能放入 327 帧；失败发生在完整混音与画面封装的边界。仅凭“超过分镜设定时长”的描述，不能断定当前任务使用了 Analysis 估时作为上限。

因此应同时排查并防止两类问题：

- 错误地把 Analysis 估时当作 Render 的硬限制。
- 把首次生成的 Render 帧数视为不可调整，混音超尾后只报错并重复执行。

### 2.2 现有代码中的相关行为

- `claude-code-video-toolkit/tools/stage_media.py` 的 `mux_scene()`：只允许归一化不足约 1ms 的纯静音边界偏差；超尾样本非零时返回 `AUDIO_MISMATCH`。
- `claude-code-video-toolkit/tools/two_stage.py` 的 `execution()`：工具异常计入修复次数，相同错误连续发生或预算耗尽后停止。
- `stage_media.py` 的 `render_scene()`：相同指纹可复用无声画面与混音；输入不变时，重试可能复用同一份必然封装失败的媒体。
- `claude-code-video-toolkit/tools/render_scene.cjs`：一次 Remotion 渲染同时生成画面和完整 PCM 混音。

“保护有效音频不被裁掉”应当保留；缺失的是可执行、可收敛的时间轴调整机制，而不是简单放宽裁剪容差。

## 三、各阶段的时长责任

| 阶段 | 负责什么 | 时长规则 |
| --- | --- | --- |
| Analysis | 切分并确认原稿 | 预估仅用于编辑器展示，不参与 Render 帧数计算 |
| TTS | 生成句级配音 | 保存每条音频、实测时长和可验证的来源记录 |
| Render 编排 | 安排字幕、人物、画面、转场及声音 | 根据真实素材建立内容时间轴 |
| 混音与封装 | 完整容纳应保留的声音，输出视频 | 按实际 PCM 样本数确定最终覆盖帧数 |
| 交付 | 全部镜头校验后统一发布 | 返回实际成片时长，不把它冒充 Analysis 预估 |

用户确认的是 `sceneId/content`。在原文和制作要求没有改变的前提下，因真实素材导致时长变化，不需要再次确认文本分镜。

## 四、阻断 Analysis 估时进入制作链

保留现有 `timing.kind=estimated` 和前端展示能力，但明确以下执行约束：

1. Render 不使用 Analysis 的 `speechSeconds`、`totalSeconds`、`totalRangeSeconds` 生成 Composition 帧数。
2. 不因成片超过预估时间而报错。
3. 实际时间轴解析函数的输入不包含 Analysis 估时字段。
4. 制作记录列出实际帧数对应的音频、转场及画面要求，便于追溯。
5. 原稿与场景标识仍取确认版本，不因时长重算而改写。

不能只增加提示词，应通过函数输入边界和回归测试保证估时不进入计算。

必须增加的测试：同一确认文本与真实音频，分别使用明显偏短、偏长的 Analysis 估时，最终制作帧数保持相同。

## 五、轻量的实际时间轴解析函数

### 5.1 职责

只做确定性的时间计算，不替模型选择画面、设计动效或改变节目内容。

输入：

- 句级配音文件、顺序和实测长度。
- 明确安排的转场及停顿。
- 音效入场位置、需要保留的有效长度。
- 必须完整展示的画面片段。
- 帧率及相关音频采样信息。

输出：当前任务的 `timeline.json`。Remotion 使用的数据文件从这份结果生成，不允许两份时间轴分别维护后产生漂移。

### 5.2 计算原则

**串行内容累加，并行内容取最大结束位置。**

```text
内容结束位置 = max(
  配音结束位置,
  必须保留的音效结束位置,
  必须完整展示的画面结束位置
)
```

片尾动画与收束配音同时开始时，不能把二者时长相加。

循环 BGM 服从内容结束位置，不参与决定节目长度，否则会形成“视频越长、BGM 越长”的循环。

具体模板要求优先保留。例如当前财经模板要求收束配音结束即结束，不能为了完整播放默认片尾音效而擅自增加业务时长；应先安排音效入场或使用范围，使其符合该要求。若素材要求与模板要求无法同时满足，明确报告冲突，不静默改变节目节奏。

### 5.3 区分三种时间

| 时间 | 含义 |
| --- | --- |
| Analysis 预估时长 | 用于展示和节奏预览 |
| 内容时间轴 | 配音、字幕、动效、BGM/SFX 的实际编排起止 |
| 最终视频覆盖帧数 | 向上取整后，完整容纳内容和固定混音的输出长度 |

内部尽量使用整数帧和整数采样数，避免反复用小数秒累计。

配音按整数帧起播时，每段按实际长度向上取整以保证容纳；字幕绑定该段配音的真实播放窗口。必须区分音频的实际长度、帧对齐窗口和最终封装覆盖长度。

不建议每条音频无条件额外加一帧：多段累计会增加停顿，也不能解决混音随着视频扩展而增长的问题。

## 六、固定完整混音，解耦音频与视频结束位置

仅修改 Composition 帧数并重新混音并不可靠。如果 BGM 随 Composition 延长，新混音仍可能超过新视频边界，导致反复加帧。

建议流程：

1. 根据内容时间轴明确所有音轨的起止和使用范围。
2. 在混音前校验每条配音的计划播放窗口覆盖实际源音频，防止上游已经截音。
3. 生成包含全部应保留声音的完整 PCM 混音。
4. 校验并固定这份混音，保存路径、摘要、采样率和样本数。
5. 根据固定混音计算最终所需的视频覆盖帧数。
6. 为封装延长画面时，不重新延长音频内容。

不能以“混音与画面等长”代替口播完整性检查：如果配音在生成混音时已经被截断，封装阶段等长也不能证明正确。

对模板自带音轨的视频素材，必须显式声明静音或保留；保留部分需要纳入内容时间轴，避免出现未登记的音轨。

## 七、结构化的封装边界调整

### 7.1 `mux_scene()` 的职责调整

- 不擅自截掉有效样本。
- 按 PCM 实际样本数检查覆盖范围。
- 将正常可处理的覆盖不足返回为结构化调整要求。
- AAC 编码延迟及填充与 PCM 内容越界分开判断，不能只比较容器报告的时长。
- 保留真正的 `AUDIO_MISMATCH`，用于错轨、偏移、内容不一致或解码失败等情况。

建议结果示例：

```json
{
  "status": "timeline_adjustment_required",
  "code": "TIMELINE_EXTEND_REQUIRED",
  "sceneId": "scene_018",
  "currentFrames": 327,
  "requiredFrames": 328,
  "sampleRate": 48000,
  "mixSamples": 523216,
  "reason": "完整混音超出当前视频覆盖范围"
}
```

上述数值对应本次报告样本；正式结果还应关联实际混音摘要和时间轴版本，不填写虚构摘要。

### 7.2 计算方式

```text
requiredFrames = ceil(mixSamples × fps ÷ sampleRate)
```

使用整数运算实现向上取整，避免浮点误差。

若实测为 48kHz、523216 个样本，30fps 下需要 328 帧。保持原混音完整，补足输出覆盖范围内剩余的静音，不裁掉这 16 个超尾样本。

## 八、有界的定向恢复

### 8.1 当前镜头

收到调整要求后，由工具执行确定的恢复动作，不让模型反复猜测帧数：

1. 更新最终视频覆盖帧数。
2. 保留原配音和已经固定的混音。
3. 同步更新 Composition 输出长度。
4. 根据该镜头允许的方式延长画面覆盖。
5. 重新封装、校验并更新记录。

对本次片尾，可保持最后一帧。正文镜头是否允许保持末帧需要结合镜头要求，不能无条件对所有场景采用同一种处理。

### 8.2 不得机械修改的内容

- 不重新请求 TTS。
- 不统一延长所有字幕结束时间。
- 不拉伸已有动画。
- 不延长循环 BGM。
- 不改变确认原稿。

现有模板若要求“最后一条配音结束帧严格等于场景帧数”，需区分内容结束与最终视频覆盖结束，允许有来源记录的封装补帧；不能为了通过校验强行延长字幕或配音窗口。

### 8.3 全片依赖

镜头长度调整后，重新计算：

- 后续镜头的全片起点。
- 章节位置及全片总帧数。
- 依赖全片时间的进度条。
- 交付清单、缓存指纹和审片证据。

不能无条件承诺只重渲染第 18 镜。当前模板各镜头均显示全片进度条，总帧数变化可能影响其他镜头的画面。

第一版建议采用简单可靠的做法：尽可能先确定所有镜头的最终时长，再进行最终画面渲染。如果最后仍需调整，重新生成实际受影响的画面，复用有效配音及混音。暂不建设复杂的跨镜头增量依赖系统。

代价：存在多渲染部分画面的可能；收益是保证章节、进度条和全片交付数据一致。

## 九、预算与收敛规则

| 情况 | 处理方式 |
| --- | --- |
| 正常首次时长调整 | 不消耗普通修复次数，仍计入执行时间 |
| 同一混音再次提出相同调整 | 禁止原样重试，报告恢复逻辑无进展 |
| 调整画面后音频又跟着增长 | 报告音频终点未固定 |
| 声音损坏、错轨或真实不同步 | 按正常失败及修复流程处理 |

调整请求绑定混音摘要和时间轴版本，防止重复消费。固定混音对应的目标帧数应当确定，不允许无限增加。

对于已经耗尽预算的旧任务，不能删除失败账本来绕过限制。修复工具后，使用明确的恢复入口或新的 Render 执行记录，继续使用原确认版本及通过缓存校验的音频；具体恢复方式在实施时对齐现有任务生命周期，不随意修改冻结输入。

## 十、建议修改范围

| 位置 | 建议修改 |
| --- | --- |
| 实际时间轴计算逻辑 | 增加小型确定性解析函数，输入不含 Analysis 估时 |
| `claude-code-video-toolkit/tools/stage_media.py` | 样本级检查、结构化调整结果、固定混音封装及恢复衔接 |
| `claude-code-video-toolkit/tools/render_scene.cjs` | 支持固定音频与画面覆盖调整，避免音频随补帧再次增长 |
| `claude-code-video-toolkit/tools/two_stage.py` | 区分时间轴调整与普通失败，保留有界恢复记录 |
| 财经模板的时间轴及相关校验 | 区分配音结束和最终视频结束，不要求字幕随封装补帧延长 |

外部 Analysis／Render 接口、文本确认及发布回调机制原则上不变。若工具结果传递层需要适配新的结构化状态，仅局部修改相关调用链，不扩大为协议重构。

相关流程文档在实施时局部更新新的时间语义与恢复规则。本文件不代表已批准修改代码、Skill、模板或其他文档。

## 十一、测试与验收

### 11.1 单元与执行链测试

- Analysis 估时变化不影响相同真实素材的最终帧数。
- 配音比预估更长或更短均可建立正常时间轴。
- 本次 10.872 秒配音、10.900333 秒混音样本最终覆盖到 328 帧。
- 固定 PCM 混音有效样本不被裁切；有损 AAC 输出另做解码与同步检查，不要求编码后字节相同。
- 精确整帧时不无故多加一帧。
- 纯静音超尾、非零样本超尾及明显音频越界分别处理。
- 转场、并行音效和片尾不错误累加。
- 循环 BGM 不引起无限延长。
- 配音播放窗口不足时在混音前失败，不掩盖源音频截断。
- 补帧不改变字幕与原配音的绑定。
- 相同调整不能反复执行，不消耗普通修复预算。
- 混音或时间轴改变后，旧缓存、清单和审片证据不会被错误复用。

### 11.2 本机 18 镜完整稿件回归

继续使用当前确认的 18 镜文本，复用通过校验的本任务音频，不重新改写原稿：

1. 18 个分镜 MP4 和合并预览全部生成。
2. 核对实测帧数、音频完整性与字幕边界。
3. 查看片尾、章节、全片进度条及拼接边界。
4. 清单记录与最终媒体一致。
5. 不再出现相同参数、相同原因连续失败三次。
6. 结果明确区分技术检查、实际看图和试听情况，不冒充已完成的人工验收。

### 11.3 Worker 集成回归

在另行获准的 Worker 测试环境验证隔离执行、结构化调整传递、所有镜头完成后的原子发布与回调。

本机回归不能代替完整 Worker 回归。不得因本文提及 Worker 验证就自行登录服务器、部署或调用客户端接口。

## 十二、建议实施顺序与最终标准

建议实施顺序：

1. 先补估时隔离及本次超尾样本的失败测试。
2. 明确内容时间轴、固定混音和输出覆盖帧数的职责。
3. 实现样本级检查及结构化调整。
4. 接入有界恢复、缓存和模板校验。
5. 本机重跑 18 镜并审查最终产物。
6. 在另行授权后进行完整 Worker 集成回归。

最终标准不是“给第 18 镜硬加一帧”，而是：**确认文本保持稳定，实际素材决定制作时长，封装差异可以自动、有限且不丢失有效音频地收敛。**

当前只完成方案整理。用户审阅无误并明确下达实施指令后，才进入开发与测试。
