# 视频制作自动调整与人工接管落地方案

> 日期：2026-09-22。状态：待审阅、待开发。
> 本次仅新增方案文档；下面的状态、接口、模块和测试均是拟实施内容，不代表已经上线。现有代码事实单独标注。
> 目标：当前视频的制作问题由 Codex 自行调整；共享代码链路的问题保存现场、暂停并交给人管理。不是遇到问题一律停止，也不是允许制作 Codex 自行修改整个项目。

## 1. 先用大白话说明最终效果

Worker 是制作负责人，Codex 是制作人员，媒体工具和最终校验是检查人员。

- 当前视频的字幕挤了、动画写错了、声音需要更长的播放时间：让制作人员改，检查通过后继续。
- 共享工具输出的格式与检查程序互相矛盾：制作人员不能修改检查标准，负责人保存现场，等待开发人员处理。
- Codex 只回复“接下来继续”，但并没有执行：Worker 检查到任务未完成，主动发起下一轮制作。
- 全部分镜、必要整片和检查记录通过以后，Worker 才发布结果。

**一次命令退出、一次 Codex 回复结束、整个任务结束，是三件不同的事。**

## 2. 当前代码中需要补齐的地方

以下是审查到的现状，不表示所有问题已经在本任务中触发。

| 位置 | 当前行为 | 缺口 |
| --- | --- | --- |
| `video-worker/src/application/execute-run.ts` | 已有执行、校验、有限修复循环 | 多类异常直接结束，缺少明确的继续制作和人工接管分支 |
| `video-worker/src/runner/codex-host.ts` | 读取模型最终 JSON；缺失或格式不符会报错 | 模型提前收尾后，未必进入按现场继续的路径 |
| `video-worker/src/contracts/two-stage.ts` | 模型阶段结果只有 `candidate/failed` | 不能清楚区分尚未完成、当前工程可修、需要人工处理 |
| `tools/stage_media.py` | 已能返回补帧信息，另有 `extend-timeline` 和 `--fixed-mix` | 正常调整仍经异常出口返回退出码 1；调用方未必接住后续动作 |
| `tools/two_stage.py` | 补帧不扣普通修复次数；其他异常一般计入失败 | 故障归属、制作修复预算、Worker 外层预算还未统一 |
| 当前本机任务的转换脚本 | 将正式时间轴改为模板格式，删除全局边界和 `audioPath` | 后续 Worker 校验仍需要这些字段；当前任务需先纠正这处脚本，不能放宽校验 |
| `queue.ts` 与数据库 | 执行状态没有人工等待状态 | 缺少保留现场、释放槽位、明确恢复的完整路径 |
| `video-pipeline` Skill | 已限制共享目录写入，也要求制作质量修复 | 部分失败规则、补帧说明和新代码尚未对齐；不能只在额外提示词里补充 |

当前本机任务使用的 `repairRounds=0` 不是推荐生产默认值；不得靠换 run、删记录或重置计数来解决恢复问题。

## 3. 权限边界：按影响范围判断，不按“是不是代码”判断

| 资源 | 制作 Codex 的权限 |
| --- | --- |
| 当前任务 `project/` 中的动画、组件、布局、工程输入 | 可修改；必须保持确认稿、输出规格和模板硬性约束 |
| 当前 run 的时间轴、props、制作清单、审查资料 | 可生成和调整；真实校验报告须由工具产生，不能伪造通过 |
| 当前任务的画面、混音和输出 | 可重新生成；收费缓存和已发布版本不能随意覆盖 |
| 确认稿、请求、输入快照、模板原件、共享工具、Worker、校验程序 | 只读 |
| 收费账本、执行预算、租约、人工恢复记录 | 仅可信工具或 Worker 可写；不能让模型直接编辑 |

模板复制到当前工程后，允许按模板声明创作本期专用内容；不等于允许删除必需人物、字幕、组件或绕过审计。

`cache/` 中普通制作缓存与收费账本必须分开保护。不能因为整个制作目录可写，就允许模型清空收费记录后重发请求。

## 4. 三层状态分别定义，不能混为一谈

### 4.1 工具结果：描述这一步发生了什么

拟统一为以下结果语义，保留具体错误码和证据：

| 结果 | 含义 | 后续动作 |
| --- | --- | --- |
| `ok` | 本步骤通过 | 进入下一步骤 |
| `adjustment_required` | 有确定处理规则的制作调整 | 调用调整工具，再检查 |
| `repair_required` | 当前工程需要 Codex 修改 | 反馈问题，修当前工程后重验 |
| `human_required` | 公共链路、权限、收费或输入风险 | Worker 确认归属后暂停 |

`TIMELINE_EXTEND_REQUIRED` 是 `adjustment_required` 的具体原因，不应表示整个任务失败。

命令行正常调整建议退出码为 0，但必须携带 `adjustment_required`；真正执行错误保留非零退出码。所有调用方必须解析结果，只有 `ok` 且产物经过验证才算步骤完成。禁止沿用“退出码为 0 就记 DONE”的批量脚本。

示例，仅展示拟新增的内部字段：

```json
{
  "status": "adjustment_required",
  "code": "TIMELINE_EXTEND_REQUIRED",
  "scope": "task_project",
  "sceneId": "scene_013",
  "details": {"currentFrames": 148, "requiredFrames": 149},
  "evidenceFile": "render/render_005/work/scene_013.adjustment.json",
  "nextAction": "extend_timeline_and_render_fixed_mix"
}
```

`nextAction` 使用受控枚举，不接受工具结果或模板提供的任意命令字符串。

### 4.2 Codex 一轮结果：描述这一轮做到哪里

Render 的拟议内部结果增加 `continue_required`、`human_required`；保留 `candidate/failed`，Analysis 暂不改动。

- `candidate`：提交候选文件，仍需 Worker 独立终检。
- `continue_required`：存在未完成步骤或当前工程待修问题，附问题记录路径。
- `human_required`：模型认为超出权限，附证据；是否进入人工状态由 Worker 判定。
- `failed`：明确终止建议；Worker 仍按可信记录判断，不能仅凭模型的 `retryable:false` 决定所有故障归属。

模型未返回合法结果，也不直接等于制作彻底失败。Worker 清理旧进程、检查当前现场；能安全继续时给出格式纠正及具体制作反馈。反复无有效进展才暂停或结束。

### 4.3 Worker 执行状态：描述任务是否还在运行

保留现有状态，新增 `waiting_human`：

```text
queued → running → succeeded
             ├── 制作调整／制作修复 → running
             ├── waiting_human → 人工恢复 → queued
             └── failed / cancelled
```

正常调整属于 `running` 内的步骤，不为每一帧建立数据库状态。人工等待不占用执行槽，也不发送“视频已失败”或“视频已成功”的最终回调。

新增状态必须同步数据库约束、类型、任务查询和运维展示，不能只往日志里写一个字符串。

## 5. Worker 如何实际发起继续制作

### 5.1 调用链

```text
executeRun
  → 检查输入、运行版本、租约和恢复现场
  → HostCodex.run（初次或带续跑反馈）
  → Codex 在当前工程制作，调用媒体工具
  → 本轮结束后停止并确认本轮子进程清理
  → 检查模型结果＋可信工具结果＋实际产物
  → 决定 continue / repair / wait_human / publish / fail
```

在现有 `execute-run.ts` 循环内实现，不新增通用工作流平台。

建议新增小型纯逻辑模块 `video-worker/src/application/render-recovery.ts`：接收检查报告和当前进度，输出处理决定。它不做渲染、不修改文件、不直接信任模型建议，可被正式 Worker 和本地驱动共同调用。

### 5.2 自动继续的具体动作

1. 检查上一轮进程是否结束，避免同一镜头被并发操作。
2. 检查当前任务和 run、确认版本、时间轴版本及未完成步骤。
3. 若为正常调整，执行已定义动作，或将动作明确交给本轮 Codex；检查未完成时由 Worker 发起续轮。
4. 若为当前工程修复，保存结构化反馈，调用 `HostCodex.run` 继续原上下文。
5. 上下文无法恢复时，读取同一任务的现场开始新模型上下文，不新建业务 run、不重新 Analysis、不扩大资料访问范围。
6. 完成后重新检查受影响部分；全部通过才能发布。

续跑反馈示例：

```json
{
  "action": "continue_production",
  "reason": "第13镜需要补帧，后续镜头尚未完成",
  "sceneIds": ["scene_013"],
  "timelineRevision": 8,
  "steps": ["更新时间轴", "复用原混音重渲第13镜", "继续剩余镜头和合片"],
  "allowedWriteRoots": ["project", "当前run制作目录", "当前run未发布输出"],
  "forbidden": ["修改共享工具", "修改确认稿", "重复不明收费请求"]
}
```

路径列表必须由 Worker 实际权限转换生成，不把这里的中文占位符直接作为接口值。

### 5.3 完成检查不是检查文件是否存在

必须检查：镜头数量和顺序、有效 MP4、源配音覆盖、字幕边界、时间轴与产物版本、真实审查记录、请求要求的整片、最终 manifest。

“下一步准备继续”不能作为终态；旧 run 的 candidate、上一轮反馈也不能覆盖本轮结果。反馈带 run、迭代序号及版本标识，Worker 拒绝过期结果。

## 6. 具体制作恢复路径

### 6.1 补一帧

1. `stage_media.py render` 保存完整混音并返回补帧信息。
2. `extend-timeline` 按记录更新时间轴，不拉长配音和字幕。
3. 从正式时间轴生成 Composition 数据、props 和相应视觉边界。
4. 目标镜头使用 `render --fixed-mix`，校验混音摘要和声音编排一致，仅重渲画面。
5. 检查输出，更新记录并继续下一镜；有全局影响时使相关旧画面失效。

当前工具的一帧上限用于封装边界，不是内容长度上限。明显超长先检查源配音、素材和实际内容编排；不能无限补帧，也不能因此重新使用 Analysis 估时。

### 6.2 源配音播放窗口不足

源配音完整但安排的播放时间不足：返回制作调整，重算句级时间轴，同步字幕和画面，重新渲染。原音频无需重新收费生成。

源音频本身损坏或内容不完整：先检查已验证副本；没有可安全复用的完整音频时转人工决定，不能静音替代或擅自重发收费请求。

### 6.3 当前动画工程错误

当前 `project/` 中组件语法错误、文字溢出、布局遮挡、动画节奏不符：Codex 可在任务工程中修复，重新进行类型检查、关键帧和必要动态片段审查，再重渲受影响镜头。

无法编译的原因如果是共享依赖损坏、工具接口不兼容，则属于公共链路。不能只看“编译失败”四个字分类；工具路径、栈信息和只读诊断应进入问题证据。

### 6.4 正式时间轴与模板输入分离

唯一正式记录仍是 `render/<runId>/timeline.json`，保存全局 `startFrame/endFrameExclusive`、句级 `audioPath/src`、实际帧数和版本。

模板的 `from/frames`、`timeline.ts`、props 从正式记录派生，不得反向覆盖正式记录。派生器本身放在可信工具中维护，当前任务只提供数据和受控工程映射；保留模板差异，不把所有模板强制改成财经模板布局。

当前黄仁勋任务的转换脚本问题应作为实施阶段的已知修复项：恢复正式字段和音频根路径，再校验现有工程。不修改 `worker_stage.py` 来接受错误地址，也不伪造缺失文件。

### 6.5 全局进度条和返工

优先按全部真实音频、明确保留的素材建立内容时间轴。各镜完整混音的采样边界确定后，再集中形成最终画面。

第一版复用已有渲染能力，不另建音频渲染引擎：首次渲染得到混音后允许进行一次统一的最终画面重渲。耗时比专门的音频预渲方案高，但减少新系统复杂度。

若某镜最终补帧影响总长或章节位置，所有依赖这些全局数据的画面都须标记待更新。单镜通过不等于整片最终版本通过。

每镜记录 `timelineRevision`、工程输入摘要和混音摘要；输入版本变化时不复用旧画面成功标记。可复用的声音不因视觉返工重新生成。若混音本身依赖的音乐起点发生变化，不能假称声音编排未变，应检查依赖并按实际情况重新混音，禁止无限追赶片尾。

## 7. 人工接管与恢复怎样实现

### 7.1 暂停流程

1. Worker 收集问题码、实际报错、涉及文件、当前步骤、已完成产物、预算和运行版本。
2. 停止本任务子进程并确认清理；清理失败时不能先释放槽位，沿用现有隔离原则。
3. 在租约保护的事务中设为 `waiting_human`，记录原因并释放槽位。
4. 任务查询显示“等待人工处理”，指出已完成到哪里，不显示“仍在渲染”。
5. 此状态不自动创建开发任务、不自动修改共享项目、不自动恢复。

第一版问题报告存在任务记录和状态查询中，不新增邮件、聊天机器人或客户端推送系统。

### 7.2 人工管理入口

拟增加仅运维角色可调用的入口，最终路由名以开发时现有鉴权约定核对：

```text
GET  /internal/runs/:runId/recovery
POST /internal/runs/:runId/resume
```

恢复请求包含幂等请求 ID、预期暂停记录版本、修复说明、批准的目标运行版本。操作者身份来自服务端鉴权，不相信请求正文自报身份。

普通客户端凭据不能自动获得运维权限。若现有服务没有运维鉴权，第一版采用受控本地管理命令复用同一恢复函数，先不开放网络恢复路由；不得上线无保护的入口。最终选择须在实施前确认。

### 7.3 恢复检查

- 任务确实处于等待状态，未取消，没有残留制作进程。
- 当前确认内容未改变；变化需走正常确认流程，不能原任务默默换稿。
- 工具升级必须有明确版本记录，不能只因为文件变了就无条件继续。
- 验证收费账本和可复用音频摘要；结果未知仍需人工核对。
- 判断需要失效的画面、混音、审查和 manifest，保留旧证据。
- 恢复事务只执行一次；重复点击不重复排队，不重复收费。

兼容修复优先恢复同一业务 run，追加恢复记录。现有“从成功版本复制到新 run”的续编接口不是本功能，不能拿它绕过当前停止标记。

若工具升级需要迁移任务数据，开发人员先提供明确的一次性迁移和检查；不能让制作 Codex 猜测如何升级共享契约。不兼容且无法安全迁移时保持人工等待，说明原因。

### 7.4 预算、截止时间和并发

人工等待不计活动执行时长；暂停时保存剩余额度，恢复排队后领取执行槽时建立新的活动截止时间，不把等待时间追加为免费执行额度。

保留历史修复次数；允许人明确追加预算时，追加值和理由须审计，不自动清零。可信恢复逻辑负责归档已解决的停止原因，不能由模型删除 `execution.json`。

数据库同任务唯一活跃约束应将 `waiting_human` 纳入，避免暂停期间提交第二个冲突 run。人工等待不被普通租约恢复器重新排队；仍允许明确取消，取消后不能再恢复。

## 8. 预算与无进展规则

- 正常调整不扣普通修复次数，但计活动执行时间并记录动作。
- 当前工程修复按一次“修复反馈到重新验收”的周期计数，不因一个周期调用多个工具重复扣费式计数。
- Worker 模式由可信执行层维护唯一预算；Python 工具记录事件并读取剩余额度，避免与 Worker 外层双重扣次数。
- 本地驱动维护同语义的文件账本，不允许生成任务自行降低限制或清空记录。
- 相同问题、相同输入和同一失败镜头集合连续无改善，触发有限次数的停止规则；初版建议连续 3 个修复周期无进展转人工，总时间上限始终有效。
- 改文件时间戳或修改无关文件不算进展；有效进展是失败项减少、步骤通过、目标边界满足。
- 明确取消或硬执行预算耗尽可以进入终态；未到上限但超出制作权限进入人工等待。

## 9. 代码修改清单

路径以仓库根为基准。新增文件名为拟定名称，实施时优先复用现有职责，不机械拆分文件。

| 文件／模块 | 具体修改 |
| --- | --- |
| `video-worker/src/application/execute-run.ts` | 接入结果分类与真实完成检查；续轮反馈；人工暂停分支；避免过期 agent-response 影响新一轮 |
| 新增 `application/render-recovery.ts` | 提供分类、下一步决定、无进展判断的可测试逻辑；不接受任意 shell 命令 |
| `runner/codex-host.ts`、`infrastructure/sandbox.ts`、`host-sandbox.ts` | 接收迭代反馈；处理提前结束和结构化状态；保留工具原始错误与来源，不丢失为纯字符串；每轮清理子进程 |
| `runner/prompts.ts` | 只适配可信请求、权限和本轮反馈；业务恢复规则来自 Skill，避免复制两份长期维护 |
| `contracts/two-stage.ts` 与共享 `two-stage.schema.json` | 定义模型阶段结果和问题记录；工具结果与候选结果各用独立结构，不混用状态 |
| `domain/task.ts`、新增数据库迁移 | 增加等待状态、问题／恢复记录、剩余预算字段或元数据；更新状态约束及唯一活跃索引，不改历史迁移 |
| `infrastructure/queue.ts`、`task-repository.ts` | 原子暂停、释放槽位、幂等恢复、等待态取消、恢复器排除等待态 |
| `application/tasks.ts`、`api/routes.ts` 或受控管理命令 | 提供鉴权后的问题查询和恢复入口；普通视频提交不能代替恢复 |
| `infrastructure/validation.ts`、`production-record.ts` | 保留问题分类与文件证据；检查最终时间轴及产物版本；候选未通过不发布 |
| `tools/stage_media.py`、`actual_timeline.py`、`render_scene.cjs` | 明确调整结果；补帧与固定混音衔接；源音频覆盖检查；画面依赖失效 |
| `tools/two_stage.py`、`worker_stage.py` | 对齐事件和预算语义、正式时间轴校验；保留暂停现场，不靠错误码字符串一律终止 |
| 模板当前工程的数据派生工具 | 保留正式时间轴；生成模板数据和 props；不覆盖模板原件和不相关栏目视觉设计 |
| `host-processes.ts`、宿主权限配置和 `threadConfig` | 核查实际挂载和写权限，保护共享工具、收费账本、预算及发布记录，不仅是提示词声明 |
| `config.ts`、`stage-workspace.ts`、`workspace.ts` | 同步有效预算和恢复版本；恢复不重新初始化或覆盖现有任务现场 |

人工等待状态会影响状态查询与取消语义，必须做兼容处理。客户端成功回调仍只返回原约定的文字和 MP4；第一版不新增客户端“等待处理”回调，不改成功结果业务结构。

内部契约变更须与宿主、工具和 Skill 同批发布并记录新 `pipelineRevision`。不能让旧消费者收到不认识的新枚举；旧任务恢复须检查并显式迁移，不能只改 Schema 后直接继续。

## 11. 本机测试如何走同一套链路

当前聊天中逐条启动命令、临时写 `set -e` 批量脚本，不能证明 Worker 的自动续跑已打通。

拟新增受控本地驱动入口，放在 `video-worker/scripts/`，直接复用 `render-recovery.ts` 的处理决定和相同制作工具。它读取现有任务目录，不调用客户端 HTTP、不登录服务器、不伪造外部回调。

模型续轮通过本地受控执行宿主完成，而不是要求用户每次在聊天里说“继续”。管理聊天用于查看结果和授权人工恢复。Linux Worker 隔离与 macOS 本地驱动的进程保护实现不同，测试报告须明确，本机目录约定不能冒充 Linux OS 隔离已通过。

本地驱动适配既有路径和运行时；不为解决本任务新增依赖安装或新的收费调用。自动调整与人工暂停的分类测试共用，同步测试本地与正式宿主适配。

## 12. 三个端到端例子

### 例一：第 13 镜补帧

148 帧不足 → 工具登记需要 149 帧 → 调整正式时间轴和派生输入 → 复用原混音重渲 → 检查通过 → 继续第 14–18 镜 → 统一更新受影响进度条 → 合片终检。期间不向用户请求“要不要补一帧”。

### 例二：当前视频动画组件错误

当前工程组件编译报错 → 返回文件和行号 → Codex 修改 `project/` 内组件 → 类型检查和实际画面检查 → 重渲目标镜头 → 继续。不能修改共享依赖或删除校验脚本来通过。

### 例三：共享工具数据契约不兼容

工具固定删除终检必要字段 → 只读诊断确认需要改公共链路 → 等待人工并保存现场 → 人批准开发修复和回归测试 → 人指定修复版本并恢复 → 校验、必要数据迁移、标记失效产物 → 继续制作。不重新 Analysis，不清收费账本。

## 13. 实施顺序与验收

### 第一批：契约、权限与恢复决定

先实现工具结果、模型结果、任务状态的区别；权限测试和纯分类测试通过后，才接执行循环。把重复预算计数问题同时对齐，避免新状态仍被旧 catch 分支终止。

### 第二批：自动制作闭环

实现续轮反馈、补帧固定混音、正式时间轴派生、版本失效与完成检查。模拟模型提前返回，确认 Worker 会继续，而不是只打印进度。

### 第三批：人工接管和恢复

实现数据库迁移、暂停清理、鉴权管理入口或本地管理命令、幂等恢复及等待预算。暂不加入复杂的跨版本自动升级系统。

### 第四批：Skill 对齐、本机驱动和完整回归

同步 Skill 和运行版本，最后重跑当前黄仁勋任务。先验证已知转换脚本问题，再使用有效双声配音缓存。全部完成前不能声称流程已经打通。

| 必测场景 | 通过标准 |
| --- | --- |
| 148→149 帧；327 帧对应混音多 16 个采样点 | 完整样本保留，自动补帧，不扣普通修复次数，并继续后续镜头 |
| 源配音窗口过短 | 渲染前发现，重算后继续；无截音、无新 TTS |
| 工程语法错误、字幕溢出 | 仅修改当前工程；审查和重渲后继续 |
| 模型提前结束、返回非法 JSON、旧候选残留 | 有界续轮，从当前现场继续，不误发布、不重头收费 |
| 共享工具报错或契约冲突 | 人工等待，制作任务未写入公共代码 |
| 时间轴缺字段或音频路径不符 | 区分当前数据遗漏和公共工具缺陷，按归属修复或暂停 |
| 后镜改变全片时长 | 相关旧画面失效，最终产物与同一正式时间轴对应 |
| 连续同问题无进展 | 有界停止并提供证据，不靠新 run 重置预算 |
| 暂停后恢复、重复恢复请求 | 只有一次排队；等待不扣活动预算；旧进程清理后才继续 |
| 暂停期间取消或提交冲突任务 | 不绕过同任务唯一活跃约束；取消后不能恢复 |
| 升级共享工具后恢复 | 校验版本与批准记录，不兼容迁移未完成则不启动 |
| 收费请求结果未知 | 不自动重发、不清账本，人工核对 |
| 18 镜、合片、最终资料校验 | 文件和真实时长、字幕、混音、版本、审查全部通过才发布 |
| 回调暂时失败 | 使用独立回调重试，不触发重新制作视频；本机测试不冒充回调验收 |

建议扩展现有 `tests/host.test.ts`、`tests/two-stage.test.ts` 和队列／数据库测试；新增恢复决定与暂停恢复测试。Python 扩展 `tests/test_actual_timeline.py`、`tests/test_two_stage.py`。既有未通过的测试要单列原因，不算入通过数。

## 14. 已知代价与明确不做

- 第一版优先可靠性，全局信息变化可能重渲较多画面；暂不做复杂依赖图和最细粒度缓存系统。
- 未知故障采用只读诊断和人工接管，可能比完全自由的自动修项目慢，但保护共享代码。
- 自动化只覆盖经过测试的确定恢复规则；新问题经人工修复并补回归后，再考虑纳入自动处理。
- 不改确认稿，不引入逐词对齐服务，不新增收费能力，不部署服务器，不改客户端成功回调结构。
- 不新增无鉴权恢复接口，不允许制作模型修改公共校验、预算或收费账本。
- 本文的开发清单不代表已执行。实施前需审阅管理入口选择、预算默认值及上述返工代价；批准后再按批次开发和验收。

**最终验收目标：当前视频能自行调整并完成；公共链路需要人修时明确暂停，修好后可核验、可恢复，而不是无声停住、无限重试或从头收费制作。**
