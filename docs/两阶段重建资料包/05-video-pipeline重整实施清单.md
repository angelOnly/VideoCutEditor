## 5. 如何保证不再并行维护两套制作路径

```text
唯一 Skill 入口
  ├─ Analysis → 文字分镜 → 返回，等待确认
  └─ Render → production-flow（唯一制作主干）
                 → 本任务工程 + 当前模板 + 受控制作工具
                 → 当前候选协议 → Worker 校验/发布
```

1. 早期源码仅用于对照，不新增一个可运行的 old-video-pipeline 与现有入口并行。
2. 重整后的 production-flow 接替当前制作规则；prompts.ts 只加载这一份。
3. 当前实际入口若调用 resolve/extend/derive，逐个迁移到职责明确的测量、任务内编排和格式适配。迁移后旧强制恢复顺序必须从 Skill、工具描述、驱动和测试中同步退出，不能只改文案。
4. 若某辅助工具仍用于其他明确场景，不因这次调整盲删文件；但不允许两阶段主入口再走旧策略。用调用检索和实际执行日志证明。
5. 对旧整片导出工具，复用其有效媒体处理能力不等于启动第二套业务流水线；同一次 Render 只选择一条明确导出路径。

## 6. 有效历史修复如何保留

后续 0c150ef 增加 tools/render_delivery.mjs、media_delivery.mjs，修复 SDR 色彩和中间音轨时序。它是修复来源，不是另一个开发基线。保留其 BT.709/像素格式、PCM 中间混音和验证思路，先测与当前逐镜导出的兼容性再复用，不能整提交搬入、硬裁声音或恢复旧 v1 接口。

旧版有效原则继续保留：实测配音驱动时间、全文保真、任务副本隔离、收费结果未知不重复请求。旧版薄弱点不照搬：仅信时间字段、渲染前截图代替最终 MP4 检查、固定两轮涵盖所有错误。

早期事实依据：DeepSeek config-check 的 148.2 秒视频有相符的交付 SHA256，报告中也明确做过色彩修复；另一早期任务有最终画面异常失败记录。参考财报成片早于 Skill 首次提交。它们说明“有成功基础，也有旧缺口”，不证明某个 Git 版本天然稳定。

## 7. 实施与验收顺序

| 步骤 | 做什么 | 通过条件 |
| --- | --- | --- |
| 1 保全 | 保存当前代码、模板、未提交修改、任务工程与音频缓存；确认没有运行任务会受影响 | 可恢复现场；资料包不能替代完整备份 |
| 2 冻结对照 | 保存当前实际入口调用图与旧版步骤对应关系 | 每项知道谁决定制作、谁执行、谁检查 |
| 3 重整主干 | 按第 4 节调整 Skill、制作工具及必要衔接 | 唯一入口，无估时约束，无冲突恢复顺序 |
| 4 本机短样 | 固定确认文本和有效音频，覆盖长字幕、双主持、音频边界、章节 | 正常调整可继续、无截音，模板效果成立 |
| 5 完整两阶段 | Analysis → 人工确认 → Render，跑黄仁勋稿及另一主题稿 | N 个真实 MP4、原稿交接、确认保真、导航连续、动态效果合格 |
| 6 接入回归 | 用现有 Worker 与回调替身测试版本、幂等、取消、修复及发布 | API 不变；任务工程可修，公共缺陷待人处理；预算不重置 |

音频边界用例包括 10.872 秒旁白与 10.900333 秒混音，不允许因旧画面长度截去有效声音；以实际媒体和模板节奏决定画面覆盖，不把某个固定补帧数变成所有视频的规则。
全部先本机测试，不登录服务器、不调用真实客户端回调、不新增未经授权收费请求。完成证据包含版本、模板摘要、输入快照、调用记录、成片、实际媒体测量和审片结论，不以“命令通过”替代。
