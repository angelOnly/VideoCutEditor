# 6 任务并发、4 个 Render 任务各 5 槽的优化方案

## 1. 结论与边界

本方案保持现有制作边界：**Codex 负责一个视频的工程、配音、时间线、分镜渲染、合片和业务终检；Worker 负责任务排队、资源上限、取消、交付校验、发布和回调。**不建设全局逐分镜渲染调度器，不把分镜拆给 Worker 执行。

目标容量为：

| 项目 | 决策 |
|---|---|
| 已受理任务数 | 不设上限，全部可在 PostgreSQL 队列中等待 |
| 活动工作流任务总数 | 最多 6 个 |
| Render 子上限 | 最多 4 个活动 Render run |
| Analysis 活动数 | 最多 `6 - 当前活动 Render 数`；Render 为 4 时最多 2 个 |
| 单个 Render 任务的分镜并发 | 固定最多 5 槽 |
| 整机分镜渲染峰值 | `4 × 5 = 20` 槽 |
| 单镜 Remotion 帧并发 | 固定为 1，不与分镜并发叠加 |

“总并发 6”是指同时启动的 Codex/systemd job 数，而不是上游一次只能提交六个视频。比如四个视频正在 Render 时，系统仍可运行两个 Analysis；第五个 Render 任务则在队列中等待。这样避免出现 `6 Analysis + 4 Render = 10` 个 Codex job 同时运行的失控情况。

任务级“6 总量 + 4 Render”调度和单任务 5 槽校验已在当前 Worker 中实现；本方案关注的是把它们配合合适的 cgroup 配额稳定落地。20 路分镜渲染和“4 Render + 2 Analysis”的混合负载尚未通过生产验收，不能仅凭任务领取逻辑上线。

## 2. 当前真实调用链与目标变化

当前 `videocut-worker.service` 是机器上的常驻服务，不随单个视频结束而退出。现有代码用六个 `execution_slots` 和 `worker.ts` 中的 6 个活动任务上限领取任务；队列在同一事务内将活动 Render 限制为 4。每条任务再启动独立的 Codex/systemd job。视频下游制作仍由该 Codex job 完成。

```text
编辑平台
  → PostgreSQL 排队
  → 常驻 videocut-worker 服务领取 run
  → 当前 run 的 Codex / systemd job
  → Codex 调用 task_io.py render
  → stage_media.py / render_batch.py 在当前任务目录渲染分镜
  → Codex 合片、终检并结束
  → Worker 校验、发布、回调
```

目标不改变 Codex 的制作职责，只增加两类受控上限：

```text
Worker：最多 6 个活动 run；其中 Render 最多 4 个
  → 每个 Codex：只可经 task_io.py render 进入渲染
      → render_batch.py 强制最多 5 路分镜并发
          → 每镜内部 Remotion 并发仍为 1
```

因此，`render_batch.py --slots` 仍是单视频内部并发度，不是全局逐镜槽池。当前代码接受 `1` 至 `5`，并由 `RENDER_TASK_SLOTS` 固定当前任务的值；本方案将生产值显式设为 `5`，不依赖默认值，也不允许 Codex 自行提高。README 中曾出现的“共享 FIFO 槽”和 `HOST_RENDER_SLOTS` 没有对应的生产实现，不能当作现有能力。

## 3. 任务状态与领取规则

分析完成后，任务等待编辑确认时不占活动任务名额。编辑确认后创建新的 Render run，再按下列规则排队：

```text
全局活动 run < 6，且活动 Render run < 4
  → 可领取下一个 Render run

全局活动 run < 6，且当前没有可领取的 Render run
  → 可领取下一个 Analysis run

全局活动 run = 6
  → 所有新 run 保持 queued
```

Render 在可用名额内优先于 Analysis：当一个 Render 完成、失败或取消，且其 systemd job 已确认停止后，活动 Render 数从 4 降到 3；若有已确认的 Render 在等待，则领取队列中最早的一个，使 Render 补回到 4。没有等待 Render 时，才用该总任务名额领取 Analysis。

例子：六个视频都完成分析并提交 Render 时，前四个进入 Render，后两个保持 `queued`；任意一个 Render 结束后，下一个排队 Render 立即开始。若同时只有两个 Render，则可再运行四个 Analysis；若已有四个 Render，则最多再运行两个 Analysis。

## 4. 历史单视频容量测试记录

### 4.1 测试条件

测试使用同一真实验收任务的 18 个分镜、同一 Remotion 工程、浏览器和素材。每轮复制独立工作目录；生产任务、生产工具和 Worker 配置均未修改。这些是历史单视频记录，保留用于估算，不代表“4 Render + 2 Analysis”的混合负载已验证。

8/12 槽测试运行于独立 systemd cgroup：CPU 配额 48 核、内存上限 96GB。12 槽分别验证了 `TasksMax=2048` 与 `4096`。这些是**单个视频任务**的数据，不代表多个视频和 Analysis 混合时已通过验收。

### 4.2 结果

| 槽位 | 轮次 | 结果 | 渲染墙钟耗时 | 关键资源/说明 |
|---:|---:|---|---:|---|
| 1 | 2 | 18/18，0 失败 | 2758 / 2761 秒 | 串行基准 |
| 2 | 2 | 18/18，0 失败 | 1411 / 1411 秒 | 并行基准 |
| 3 | 2 | 18/18，0 失败 | 954 / 953 秒 | 并行基准 |
| 8 | 1 | 18/18，0 失败 | 374 秒 | 内存峰值 14.1GB，PID/线程峰值 1601 |
| 8 | 2 | 18/18，0 失败 | 378 秒 | 内存峰值 14.1GB，PID/线程峰值 1592 |
| 12 | 1 | 1 成功、9 失败后停止 | 84 秒 | `TasksMax=2048`，PID/线程达到 2045 后报资源不足 |
| 12 | 2 | 18/18，0 失败 | 325 秒 | `TasksMax=4096`，内存峰值 20.5GB，PID/线程峰值 2389，平均约 26.1 核 |

8 槽已连续两次成功。12 槽在足够 PID 配额下成功一次，比 8 槽约快 13%，但内存多约 45%，并显著提高 PID/线程数。该任务只有 18 镜，后半段会出现少数长镜头拖尾，更多槽不能持续利用。

20 槽的粗略线性估算约为 43.5 个平均 CPU 核、34GB 内存、3980 PID/线程；四份独立工程会重复启动 bundle、Chrome 和 Node，实际数值可能更高。因此该估算仅用于制定压测配额，不作为生产结论。

## 5. 2026-09-24 真实任务故障复盘

### 5.1 发生了什么

本次任务只运行了 **1 个 Render job × 5 条分镜并发**，并没有触发“4 个 Render job”的外层上限。分析阶段成功；Render 的 18 条分镜中 `scene_018` 成功，另 6 条在 4% 至 6% 的相近进度陆续失败。

时间线与系统证据如下（UTC）：

| 时间 | 证据 | 结论 |
|---|---|---|
| 10:00:35 | 内核记录 `cgroup: fork rejected by pids controller`，归属当前 Render 的 systemd job | 当前 job 已触达 PID/线程上限，新的浏览器或编码子进程无法创建 |
| 10:00:36 | `scene_012` 首先报 `write EPIPE` | 进程创建受限后，Remotion 内部通信管道出现下游写失败 |
| 10:00:53 至 10:02:20 | 其余 5 条分镜依次报相同错误 | 这是同一资源边界的连锁表现，不是六条分镜内容同时出错 |
| 10:01:50 | `scene_018` 完成 | 模板、脚本与工程本身可渲染；先取得资源的分镜可成功 |

本次 Render job 的 `TasksMax=1024`；其内存峰值为 7.3GB，低于 12GB 的 `MemoryMax`，且没有 OOM 记录。直接根因是 **单个 Render cgroup 的 PID/线程上限 1024**，不是内存不足，也不能把 `EPIPE` 误判为单纯的进度日志错误。

`EPIPE` 是下游症状：某个 Remotion/浏览器/FFmpeg 子进程未能创建或已退出后，Node 往内部通信管道继续写入而失败。进度日志也应当做安全降级，但它不是本事故的第一根因。

### 5.2 三层并发与 PID 口径

| 层级 | 上限 | 本质 | 本次关联 |
|---|---:|---|---|
| Worker 活动 run | 6 | 同时运行的 Codex/systemd job 总数 | 4 个 Render 时最多再运行 2 个 Analysis |
| 活动 Render run | 4 | 同时处理的不同视频数 | 不是单视频分镜数 |
| 单个 Render 的分镜槽 | 5 | 同一个视频内同时启动的分镜渲染根任务 | 4 个 Render 满载时为 `4 × 5 = 20` 条分镜根任务 |
| 单镜 Remotion 帧并发 | 1 | 单条分镜内部帧编码并发 | 不得与 5 槽相乘提高 |

一个“分镜槽”不是一个 Linux 进程。它会展开为 Node、Chromium 主进程及多个子进程/线程、Remotion、FFmpeg 等；`TasksMax` 统计的是进程和线程任务总数。

当前 `TasksMax=1024` 是**每个 job**的限制，不是服务器总上限。按当前静态配额，4 个 Render job 最多可占用 `4 × 1024 = 4096` 个 PID/线程任务；若全局 6 个活动 run 都被用满，则还可能有 2 个 Analysis job，静态配额合计最多为 `6144`。这不是已验证的安全容量：本次单个 Render 已在 1024 处被拒绝继续 fork，说明现有配额不支持“1 Render × 5 槽”。

服务器物理资源为 56 CPU 核、125GiB 内存；内核 PID 上限为 4,194,304，用户级与 Worker 父 cgroup 均未设置 1024 上限。因此要调整的是**每个 Render job 的 cgroup 配额**，不是提升服务器内核 PID 上限。

## 6. 落地改造范围

### 6.1 单任务渲染工具与错误分类

在 `claude-code-video-toolkit/tools/render_batch.py` 与 `stage_media.py`：

1. 保持现有 `1` 至 `5` 的槽位校验；在 Worker 部署配置中显式设置 `RENDER_TASK_SLOTS=5`，不以默认值、Codex 提示词或模型自行拼出的参数作为容量边界。
2. `render_scene.cjs` 保持 `concurrency: 1`，避免单镜帧并发与五路分镜并发相乘。
3. 在 `stage_media.py` 的子进程失败路径读取当前 cgroup 的 `pids.current`、`pids.max` 与 `pids.events`。若 `pids.events.max` 在本次渲染期间递增，返回结构化错误 `PROCESS_LIMIT_EXCEEDED`，并带上实际峰值与配额，而不是只向上游暴露 `EPIPE`。
4. `render_batch.py` 仅在 `PROCESS_LIMIT_EXCEEDED`、进程清理失败或共享浏览器不可用时停止继续派发新分镜；已启动分镜应等待收敛，成功产物保留。单条分镜的工程/素材错误仍允许其余分镜继续，不能把普通 `RENDER_FAILED` 一律 fail-fast。
5. `render_scene.cjs` 的进度输出改为安全写入：日志管道异常只停止进度上报，不可让已健康运行的 MP4 编码进程退出。最终成功仍以 `done.json`、MP4 与媒体校验为准。
6. 批次进度中记录实际槽位数、每镜耗时、`pids.current` 峰值、`memory.current` 峰值、失败分类和已保留分镜，供 Worker 与页面展示诊断。

Codex 仍选择、生成或修复视频工程；它不再能把单个任务提升到 6 路及以上。

### 6.2 Worker 的总并发与 Render 子上限

在 `video-worker` 做任务级调度调整，不新增逐镜数据模型：

1. 已有迁移已将 `execution_slots` 扩为 6 个，`worker.ts` 的活动任务上限也已为 6；本次不重做迁移。
2. `Queue.claim` 已在同一 PostgreSQL 事务内锁定容量状态、统计活动 Render run，并选择“总活动数未满 6 且活动 Render 少于 4”的 Render run；现有回归测试覆盖“4 Render + 2 Analysis”及 Render 结束后补领排队 Render，后续不得仅靠 Worker 内存计数替代。
3. Render 已满 4 时，领取逻辑必须跳过排队 Render，选择 Analysis 以填满剩余总名额；Render 未满且有排队 Render 时，优先领取最早的 Render。
4. Render 成功、失败或取消时，先确认对应 systemd job 已停止，再释放执行槽并唤醒下一轮领取；取消、租约失效和重启恢复时同样重新核对这两个上限。

不新增 `render_slots`、`render_batches`、`scene_render_tasks` 等表，不把分镜拆给 Worker。新增的是任务阶段级、数据库事务保护的“6 总量 + 4 Render”领取规则。

### 6.3 systemd 资源配额与候选配置

当前生产环境通过通用 `HOST_TASK_*` 向两个阶段都传入 16 CPU、12GB、1024 PID；因此单个 Render 在 5 槽下撞到了 1024 PID/线程边界。应改为按 run 阶段传入独立档位：

| 资源 | 单个 Render job 候选值 | 单个 Analysis job 候选值 | 峰值 `4 Render + 2 Analysis` | 说明 |
|---|---:|---:|---:|---|
| CPUQuota | 1200% | 200% | 5200% | `4 × 12 + 2 × 2 = 52` 核，低于 56 核并为系统留余量 |
| MemoryMax | 16GB | 4GB | 72GB | 为独立工程、浏览器及 Analysis 保留余量 |
| TasksMax | 2048 | 512 | 9216 | 当前 5 槽已触达 1024；2048 是候选值，必须以混合负载实测校准 |
| 分镜并发 | 5 | 不适用 | 20 | 每镜帧并发固定为 1 |

对应环境变量为 `HOST_RENDER_TASK_CPUS`、`HOST_RENDER_TASK_MEMORY`、`HOST_RENDER_TASK_PIDS` 以及 `HOST_ANALYSIS_TASK_CPUS`、`HOST_ANALYSIS_TASK_MEMORY`、`HOST_ANALYSIS_TASK_PIDS`。未设置阶段专用变量时，它们会回退到通用 `HOST_TASK_*`，这正是本次两个阶段共用 1024 PID 配额的原因。

首轮验收的候选配置如下；它只在完成第 6.1 节的错误分类与指标采集后启用：

```dotenv
RENDER_TASK_SLOTS=5
HOST_RENDER_TASK_CPUS=12
HOST_RENDER_TASK_MEMORY=16G
HOST_RENDER_TASK_PIDS=2048
HOST_ANALYSIS_TASK_CPUS=2
HOST_ANALYSIS_TASK_MEMORY=4G
HOST_ANALYSIS_TASK_PIDS=512
```

这些是 cgroup 的隔离和保护边界，不代表机器已经证明能稳定运行该组合。所有子进程必须位于各自任务 systemd cgroup；取消时按已有 `KillMode=control-group` 清理。

### 6.4 实施顺序

1. 为 `stage_media.py` 和 `render_batch.py` 增加 cgroup 指标采集、`PROCESS_LIMIT_EXCEEDED` 分类和仅针对共享资源故障的停止派发逻辑；为 `render_scene.cjs` 增加安全进度写入。
2. 补充单元测试和 Linux 受控回归：验证普通分镜错误不会停止其他分镜，PID 上限错误会停止新派发并保留成功结果，且退出后没有活动子进程记录。
3. 提交、部署上述代码后，在 Worker `.env` 写入第 6.3 节候选配置，重新安装 Worker systemd user service；确认新 job 的 `CPUQuota`、`MemoryMax`、`TasksMax` 与预期一致。
4. 按第 7.1 节逐级进行网页提交的两阶段验收。任何一轮失败先回滚并复盘指标，不继续提升并发。

## 7. 验收、灰度与回滚

### 7.1 分阶段验收顺序

不要直接以四个真实视频同时压满资源。按下列顺序在独立验收环境执行，每轮均使用独立任务目录、同一类模板和完整两阶段网页提交流程：

1. **单 Render × 5 槽**：验证 `TasksMax=2048` 后不再出现 `fork rejected` 或 `PROCESS_LIMIT_EXCEEDED`；若出现日志通道 `EPIPE`，必须被分类为非致命日志异常且不影响 MP4 校验与交付。记录单 job 的 PID、内存和 CPU 峰值。
2. **2 Render × 5 槽 + 4 Analysis**：验证两个 Render 不互相影响，Analysis 可填满剩余任务位；检查 Render 总数不超过 4、活动 run 不超过 6。
3. **4 Render × 5 槽 + 2 Analysis**：这是目标混合负载。四个视频必须是独立工作区；不能复制同一任务目录或绕过网页确认直接写数据库。
4. **取消与恢复**：在满负载时取消一个 Render；确认只回收该 job 的 cgroup，其他 3 个 Render 和 2 个 Analysis 持续运行；排队的第五个 Render 仅在名额释放后领取。

第 3 步按第 6.3 节候选配额运行。验收要求：

- 四个 Render 都完成分镜、合片、终检、发布与回调；两个 Analysis 均不因资源争抢失败；
- 任一 Render 的实际分镜并发不超过 5，整机同时渲染不超过 20；总活动 Codex job 不超过 6；
- 无内核 `fork rejected by pids controller`、`EAGAIN`、`PROCESS_LIMIT_EXCEEDED`、浏览器残留、cgroup 越界、PID 耗尽、长时间 CPU 节流或磁盘 I/O 堵塞；单独出现的安全降级日志 `EPIPE` 必须不影响有有效 MP4 的分镜交付；
- 分别记录每个 job 的 `memory.peak`、`pids.peak`、`pids.events`、`cpu.stat`、总耗时和失败率；`pids.events.max` 必须为 0，PID 与内存峰值应至少保留 20% 配额余量；
- 取消一个 Render 不影响其余三个 Render 和两个 Analysis；排队的第五个 Render 仅在名额释放后启动；
- 重启 Worker 后不突破“6 总量 + 4 Render”上限，不让旧进程重复提交产物。

通过后先灰度真实业务任务；若资源或稳定性不达标，先将 `RENDER_TASK_SLOTS` 回退为 2，并保持“总 6、Render 4”的任务级调度不变。暂停新增 Render run 不应影响已完成产物、Analysis 结果或回调重试。

### 7.2 明确不在本次范围内：4 视频 × 6 槽

机器规格为 56 核、125GB 内存，因此“4 个视频各 6 槽、共 24 槽”值得在本方案稳定后测试，但不能据 12 槽单视频结果直接认定可用：12 槽平均已占约 26.1 核；按近似线性估算，24 路可能接近或超过本次 48 核 CPU 配额。PID/线程也可能超过 4096，且四份工程的重复进程会放大开销。

24 槽压测必须仍采用真实形态：4 个独立视频、每个固定 6 槽，并保留两个 Analysis，记录整机与每个 cgroup 的 CPU、内存、PID、I/O、耗时、失败和取消恢复。只有连续多轮零资源失败并保留余量后，才可由“4×5”调整为“4×6”。在此之前，不修改当前单任务 1 至 5 槽的代码上限。

### 7.3 回滚条件与操作

出现以下任一条件即停止扩大负载并回滚到单 Render 2 槽：任一 `pids.events.max` 增长、内核出现 `fork rejected`、任一 job 超过 80% 的 PID 或内存配额、共享浏览器异常导致两个及以上分镜失败、整片校验或发布失败。

回滚只调整阶段专用资源变量和 `RENDER_TASK_SLOTS`，随后重新部署 Worker；不删除任务目录、不重做已成功 Analysis、不覆盖已完成的分镜或回调记录。恢复任务必须使用当前已冻结的批次并经网页正常确认流程继续。

## 8. 已知代价

- 上游可无限提交，但第七个及后续活动任务会等待；这是用明确的机器容量换取稳定性的正常排队。
- Render 优先补满至 4，重 Render 高峰下 Analysis 可能等待；这是保证已确认视频尽快交付的取舍。
- 单个空闲视频固定最多 5 路，不会获得单视频 8/12 路的最短墙钟时间；换来的是实现简单和四视频同时推进。
- 本方案只做任务级公平，不具备逐镜公平调度。若未来需要动态将 20 路在不同视频的分镜间重新分配，才需要另建全局 Render Gate 或 Coordinator。
