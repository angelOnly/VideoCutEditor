# 两阶段视频创作流程优化方案

## 1. 背景与目标

当前线上 `video-two-stage/1` 已验证以下链路可用：Worker 接收任务、冻结模板 ZIP、执行 Analysis、接收客户端确认、执行 Render、发布结果并回调客户端。

但最近一次财经双人对话测试的成片存在三个明显问题：

1. 正文动效较少，效果接近静态信息卡；
2. 没有随 TTS 播放的句级字幕；
3. 模板包含说明和素材，但缺少可复用的栏目制作组件，Render 每次从零生成正文工程，质量不稳定。

本方案的目标是：**不改变四个对外接口和两阶段边界，让 Codex 在 Render 阶段对最终视频效果负责，并使财经双人对话模板稳定产出与模板参考成片一致的栏目观感。**

## 2. 唯一验收基准

本方案不用 DeepSeek 成片作为验收基准。DeepSeek 只可作为历史实现资料，不属于财经双人模板的栏目标准。

唯一视觉、节奏和声音基准为模板包内的参考成片：

```text
财经双人对话视频生成指令/
└── assets/video/reference/
    └── financial-report-dialogue-v3-final-cut-preview.mp4
```

仓库中的绝对路径：

```text
/Users/jiang/Documents/VideoCutEditor/claude-code-video-toolkit/
deliverables/财经双人对话视频生成指令/assets/video/reference/
financial-report-dialogue-v3-final-cut-preview.mp4
```

该文件为 16:9、30fps、约 149 秒的预览成片。它用于比对栏目语言，不要求新视频复用其中的事实、文案、旧配音或逐镜内容。

验收时应比对以下维度：

- 双主持人高亮、弱化及切换节奏；
- 底部句级字幕、关键结论卡和数据面板的层级关系；
- 数据、图形、数字和风险提示随旁白递进出现的节奏；
- 章节卡、片头、片尾的转场语法；
- 背景音乐、章节音效和数据音效的克制使用；
- 非静态 PPT 的动效密度和整体财经栏目观感。

分辨率可以是最终交付要求的 1920×1080；参考成片的 960×540 只是不影响比例的预览编码，不作为像素尺寸限制。

## 3. 职责边界

### 3.1 Worker：只管理任务，不参与创作

Worker 的职责保持为：

- 接收四个既有接口请求、校验任务身份和版本；
- 排队、并发控制、取消、重试、阶段状态和任务目录隔离；
- 下载、校验、冻结并在两个阶段复用同一份模板 ZIP；
- 持久化 Analysis 方案、Render 结果和回调 outbox；
- 通过既有客户端回调接口发布结果；
- 向 Codex 提供受控的任务目录及工具调用通道。

Worker **不**决定以下内容：

- 不选择角色、镜头、音色、字幕、动效、音乐或素材用法；
- 不生成或重写 Remotion 正文工程；
- 不规定何时调用 TTS、FFmpeg、Remotion 或审片脚本；
- 不以通用布局替代模板的栏目视觉。

`video_tts`、受控命令执行和媒体工具只是 Codex 可调用的基础能力，不是由 Worker 编排的创作流程。

### 3.2 Codex：对创作与最终效果负责

Codex 通过 `video-pipeline` Skill 完成两个阶段；Skill 中的脚本调用时机由 Codex 根据当前任务决定。

| 能力 | 责任方 |
| --- | --- |
| 文本分镜、角色分配、画面创意 | Codex |
| TTS 分句、音色使用、音频时长测量 | Codex |
| 字幕分页、内部时间轴、动效与音效编排 | Codex |
| Remotion 工程创建或改造、FFmpeg/Remotion 调用 | Codex |
| 关键帧及动态效果审查、修复后复验 | Codex |
| 任务状态、回调、发布、隔离与重试账本 | Worker |

Render 结束前，Codex 对“字幕是否跟随口播、动效是否按旁白递进、画面是否符合模板参考成片”负责；技术上成功导出 MP4 不是完成标准。

## 4. 两阶段职责重整

### 4.1 Analysis：快速文本分镜，不进行媒体制作

Analysis 的目的是让客户端编辑、确认文案与分镜，而不是提前完成制作时间轴。

Analysis 只输出已有回调结构中的文本分镜；每镜最小包含：

```text
- sceneId；
- 原稿对应文本（可按自然句或短段拆分，但不得改变原意）；
- 发言角色；
- 镜头目的，例如钩子、追问、解释、数据结论或收束；
- 一句简短画面意图，例如“五层阶梯图，最后强调应用层”。
```

Analysis 不做以下事项：

- 不调用 TTS；
- 不生成音频、视频或正式图片；
- 不测量音频时长；
- 不输出 `startFrame`、`endFrame`、字幕帧或音效帧；
- 不要求模型在回调前实现 Remotion 页面；
- 不把复杂技术时间轴暴露给客户端编辑。

这意味着 Analysis 的主要耗时应是阅读稿件、模板和素材说明后的单次文本规划，不包含媒体生成和画面修复循环。

客户端可在现有 Analysis 回调的 `dataList` 中编辑文本、角色和镜头意图，再按现有 Render 提交接口确认。无需新增接口或改变四个路由。

### 4.2 Render：完整创作阶段，对最终效果负责

Render 读取客户端确认后的分镜、冻结的同一份模板 ZIP、任务素材和参考成片。它是完整的制作阶段，执行顺序如下：

1. 读取模板说明、栏目基线源码、参考成片和确认分镜；
2. 保留确认稿件与镜头顺序，将每镜口播按自然句拆成内部发言单元；
3. 由 Codex 自行调用 TTS，并用实际生成音频测量每个句子的时长；
4. 根据真实音频建立仅供本次任务使用的内部 `timeline.json`；
5. 复用模板的栏目基线组件，并为本期稿件新增专属数据图解、场景和动效；
6. 调用 Remotion 与 FFmpeg 渲染；
7. 查看人物切换、章节、字幕、关键数据出现、片尾和完整动态片段；
8. 未达到模板参考成片的栏目观感时，修工程后重新渲染并复验；
9. 通过后发布当前接口所需的分镜结果及任务内完整审计资料。

Render 可以决定具体的技术实现和脚本调用顺序，但必须遵守客户端确认的原文、角色、分镜顺序、模板素材边界和输出规格。

## 5. 句级字幕策略

字幕必须恢复为句级字幕；它与主持人旁的“关键结论卡”同时存在，二者用途不同：

| 图层 | 内容 | 目的 |
| --- | --- | --- |
| 关键结论卡 | 8～18 字的重点结论或提问 | 强化栏目节奏和信息重点 |
| 底部句级字幕 | 当前正在播放的自然句全文 | 让观众跟随 TTS 理解口播 |

不采用中文逐字、逐词声学对齐，也不安装或依赖额外 ASR 对齐服务。实现方式为：

1. Codex 在 Render 中按自然语义和标点拆分 TTS 句子；
2. 每个句子单独生成 TTS；
3. 使用该句音频的实际起止时间作为字幕起止时间；
4. 句子过长时继续拆为自然短句或字幕页，避免溢出安全区；
5. 底部字幕随句切换，不能用预估字数推算时长。

这样得到的是可靠的句级同步：不要求中文逐词精确，却不会因为缺少对齐服务而让任务失败。

## 6. 模板 ZIP 的最小补充

### 6.1 现有素材继续保留

现有 ZIP 中的说明文档、头像、Logo、BGM、SFX、片头、片尾、引导图和参考成片继续保留。它们是栏目资产，不应在 Render 中替换为临时占位素材。

### 6.2 新增“栏目基线源码”，不是旧案例源码

ZIP 新增 `renderer/`，只包含通用、可复用的财经双人栏目能力：

```text
财经双人对话视频生成指令/
├── 财经双人对话视频生成指令.md
├── assets/
└── renderer/
    ├── src/
    │   ├── Root.tsx
    │   ├── FinancialIntros.tsx
    │   ├── SpeakerStage.tsx
    │   ├── SubtitleLayer.tsx
    │   ├── ChapterTransition.tsx
    │   ├── AudioLayer.tsx
    │   └── VisualBlocks.tsx
    ├── package.json
    ├── tsconfig.json
    ├── renderer-manifest.json
    └── timeline.example.json
```

各文件的边界如下：

| 文件/组件 | 保留的通用能力 | 不得包含的内容 |
| --- | --- | --- |
| `FinancialIntros.tsx` | 栏目片头、片尾、通用光效与转场 | 某一期的公司、标题、配音和脚本 |
| `SpeakerStage.tsx` | 男女主持人位置、高亮、弱化、切换动效 | 某一期的对话文本 |
| `SubtitleLayer.tsx` | 句级字幕样式、安全区、分页和切换动效 | 历史字幕内容与时间轴 |
| `ChapterTransition.tsx` | 章节卡样式与进退场 | 历史章节标题 |
| `AudioLayer.tsx` | 连续 BGM、SFX 混音和淡入淡出规则 | 历史 TTS 文件 |
| `VisualBlocks.tsx` | 指标卡、对比、因果链、层级图、趋势、引用卡等通用图解 | 某一期的数据、结论或图表配置 |
| `timeline.example.json` | 字段示例和组件输入示例 | 可被误用的旧业务数据 |

`FinancialIntros.tsx` 属于通用栏目源码，适合加入 ZIP；当前 DeepSeek `Episode.tsx` 一类包含特定稿件、时间点和数据的页面不应加入。

### 6.3 基线源码的使用方式

模板 ZIP 中的源码不能作为未知脚本直接执行，也不在任务内安装依赖或运行模板自带命令。

安全、可控的方式是：

1. Worker 在 Analysis 时验证、冻结 ZIP 与文件摘要；
2. Render 时将已准入的 `renderer/` 静态源码复制到本次任务的 `project/`；
3. Codex 只使用服务端已部署、已锁定版本的 Remotion 依赖；
4. Codex 在任务副本中创建本期 `timeline.json`、Props 和专属场景组件；
5. 所有生成代码、TTS、视频和审计文件只写入本次任务目录。

这不会限制创作。栏目基线固定“这个节目如何呈现”，本期专属场景决定“本期讲什么、怎样解释、用什么图解和动效”。

## 7. Render 内部时间轴

技术时间轴从 Analysis 移至 Render 内部生成，不作为客户端确认时的负担。

每个句级发言至少记录：

```json
{
  "sceneId": "scene_003",
  "utteranceId": "scene_003_sentence_02",
  "speaker": "male-chief",
  "text": "美国在最关键的应用层已经落后。",
  "audioPath": "tool-audio/xxx.mp3",
  "startFrame": 120,
  "endFrameExclusive": 258,
  "caption": {
    "text": "美国在最关键的应用层已经落后。",
    "startFrame": 120,
    "endFrameExclusive": 258
  }
}
```

视觉块和音效也由 Render 依据真实 TTS 时间计算：

```json
{
  "kind": "five-layer-stack",
  "sceneId": "scene_003",
  "startFrame": 148,
  "endFrameExclusive": 360,
  "props": {"highlight": "应用层"},
  "sfx": [{"name": "risk-alert.wav", "frame": 270}]
}
```

时间轴必须由 Codex 实际写入、实际用于 Remotion Composition，并在审片记录中引用；不能只在 Analysis 写描述、Render 再用硬编码延迟替代。

## 8. Render 的质量门禁

Render 不能只检查首、中、尾静帧。它至少需要审查以下动态区间：

1. 每次主持人切换的前后片段；
2. 每个章节卡的入场、停留和退出；
3. 每个关键数字、对比、趋势或风险结论的出现时点；
4. 至少一组连续句级字幕切换；
5. 片头与正文衔接；
6. 最后一句、片尾和 BGM 淡出的同步；
7. 整体音量关系：对白优先，BGM 与 SFX 不抢词。

每轮审查应记录：实际查看的媒体片段或帧、发现的问题、修改的组件/时间轴、重新验证结果。以下情况不得发布：

- 只有关键结论卡，没有句级字幕；
- 数据或图形在旁白开始时一次性全部出现；
- 主持人没有随说话人切换；
- 章节卡与人物正文同屏；
- 背景音乐在每个分镜开头突兀重启；
- 使用静态 PPT 式正文替代模板参考成片的动态栏目节奏；
- 仅因 MP4 可解码就判定成功。

## 9. 连续 BGM 与现有回调

财经栏目参考成片使用整片连续 BGM。当前 Worker 回调以 `dataList` 发布逐镜视频，现有两阶段发布代码只发布确认分镜产物。

本次不改变四个对外接口路由，但实施前需要确认客户端的最终消费方式：

1. **客户端需要完整成片**：Render 生成整片 Composition，并在既有回调报文可扩展的数据字段中提供整片资源；路由不变，但客户端需要确认是否读取该字段。
2. **客户端只消费逐镜 MP4**：分镜应保留完整对白、字幕和画面；连续 BGM 的整片版本作为 Worker 内部预览与审计产物。客户端侧拼接时需要按当前产品规则处理 BGM，不能把每段都从音乐开头直接拼接。

该项是媒体交付表现问题，不是创作权归属问题；无论最终消费方式如何，BGM、SFX、字幕和画面编排均由 Codex 在 Render 中决定。

## 10. 实施步骤

### 第一步：补齐模板制作基线

1. 从现有财经栏目工程中提取通用组件；
2. 删除所有历史稿件、TTS、旧时间线和特定数据；
3. 将通用组件、`renderer-manifest.json` 和字段示例加入模板目录；
4. 更新 ZIP；
5. 校验 ZIP 可解压、路径唯一、组件引用的素材均存在。

### 第二步：调整模板说明

模板文档明确：

- 对话结论卡不等于字幕；句级字幕必须存在；
- Analysis 只输出文本分镜，不输出技术帧；
- Render 自行负责 TTS、内部时间轴、动效创作、渲染与审片；
- 通用栏目组件必须复用；本期图解与场景由 Codex 创作；
- 模板参考成片是唯一验收基准。

### 第三步：调整 `video-pipeline` Skill

Skill 需要改为：

- 明确 Worker 不是创作编排者；
- 将 Analysis 限定为快速文本分镜；
- 将 TTS、内部时间轴、Remotion、FFmpeg、审片和修复全部归属 Render；
- 规定 TTS 按自然句生成，句级字幕使用真实音频边界；
- 要求复制模板基线源码到任务工程并实际导入使用；
- 要求 Render 对照模板参考成片进行动态审查；
- 禁止用临时静态卡片工程替代模板基线，除非模板明确不提供基线源码。

### 第四步：最小 Worker 适配

Worker 保持任务管理职责，只做必要适配：

- 将模板 `renderer/` 作为已冻结、可复制的任务资料；
- 维持当前受控写目录和工具通道；
- 不增加财经模板专用布局分支；
- 不改变四个接口路由、请求方向或阶段状态；
- 若确认需要向客户端交付完整成片，再以现有回调 DTO 的兼容字段发布该资源，不新增路由。

### 第五步：服务器真实两阶段回归

在服务器上使用同一篇固定测试稿，按真实客户端请求顺序执行：

1. 调用 Analysis 接口；
2. 检查回调中的文本分镜，确认 Analysis 未生成媒体产物；
3. 使用原样或编辑后的完整分镜调用 Render 接口；
4. 检查 Render 回调、任务审计资料、句级字幕时间轴和真实视频；
5. 人工对照模板参考成片审看；
6. 记录通过项和差异，不将 DeepSeek 成片作为验收依据。

## 11. 验收清单

### 接口与阶段

- [ ] 四个既有接口路径、请求方向、鉴权和回调方式不变；
- [ ] Worker 不生成镜头、字幕、动效或 Remotion 正文工程；
- [ ] Analysis 只返回可编辑文本分镜；
- [ ] Render 只使用同一任务冻结的 ZIP、确认方案和登记素材；
- [ ] 客户端确认后才开始 TTS 和渲染。

### 成片效果

- [ ] 16:9、1920×1080、30fps；
- [ ] 所有口播均有句级字幕；
- [ ] 字幕随相应句级 TTS 的真实边界切换；
- [ ] 对话结论卡保持简短，不替代字幕；
- [ ] 主持人高亮、弱化和切换符合模板参考成片；
- [ ] 数据图解、数字与风险提示按旁白逐步出现；
- [ ] 章节卡、片头、片尾符合模板节奏；
- [ ] BGM 与 SFX 不抢对白；
- [ ] Render 已查看动态片段并完成问题修复；
- [ ] 成片栏目观感与模板参考成片一致，不退化为静态 PPT。

## 12. 已知代价与边界

- Render 的工作量会高于当前临时生成静态卡片的方式，因为它需要实际创作、审片和修复；这是换取稳定质量的必要成本。
- Analysis 因不做 TTS、渲染和技术时间轴，整体应显著缩短；具体耗时仍取决于稿件长度和 Codex 读取模板所需时间。
- 栏目基线保证风格下限，不要求不同稿件复制同一套图表；新主题仍由 Codex 创作专属场景。
- 新模板若希望达到同等稳定性，也需要随 ZIP 提供自己的栏目基线源码和参考成片；仅提供 Markdown 加素材时，只能获得“按说明创作”的效果，不能保证固定栏目品质。
- 完整成片是否直接随现有回调提供，需要先确认客户端对逐镜 MP4 与整片资源的消费方式；这不影响四个接口路由。
