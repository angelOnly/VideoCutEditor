## 0. 先把耗时现象、证据和原因连起来

### 0.1 本次究竟慢在哪里

本次从 Analysis 启动到最终回调约 1小时20分23秒，其中 Render 为 1小时18分18秒。用户调查中的阶段分布如下；表内时间已取整，相加可能与精确总时长相差约一秒。[H1]

| Render 工作区间 | 约耗时 | 对优化判断的意义 |
| --- | --- | --- |
| 读资料、设计、配音、初版代码 | 8分47秒 | 混合了创作和工程准备，不能全部当成浪费 |
| 同一代表段试作、检查、修改 | 18分40秒 | 试错使用了昂贵的完整导出路径 |
| 第一轮正式批量渲染 | 17分40秒 | 必须完成的实际制作，需与上一版单轮比较 |
| 整理交付并补设计索引 | 2分12秒 | 原本可提前发现的资料缺项在末尾暴露 |
| 第二轮正式批量渲染 | 17分36秒 | 纯记录补写触发整批重做，是最明确的返工 |
| 补审片图片及检查 | 5分29秒 | 工具默认取证与最终规则之间存在缺口 |
| 合片、最终检查、回传 | 7分55秒 | 含必要交付和潜在重复检查，不能整体删除 |

不能把“Render 78分钟”理解成“视频编码跑了78分钟”。它包含理解、创作、工具等待、试错、生成、取证和交付。优化对象必须具体到哪一类工作、为什么发生、能否避免。

### 0.2 为什么把返工排在参考库和并发前面

对比已有双类型参考库的 1.3.0 与增加制作门槛的 1.4.0，用户记录是：[H1]

| 对比项 | 1.3.0 | 1.4.0 | 能得出的判断 |
| --- | --- | --- | --- |
| Render 总耗时 | 33分38秒 | 78分18秒 | 新增44分40秒 |
| 正式批次前准备 | 4分48秒 | 27分27秒 | 新增22分39秒 |
| 正式批次执行合计 | 16分35秒 | 35分17秒 | 新增18分42秒，主要多了一轮 |
| 其余整理、修复与交付 | 12分15秒 | 15分34秒 | 新增3分19秒，不能全归给某个检查器 |
| 成片时长 | 139.1秒 | 152.633秒 | 新片更长，两次并非严格同输入 |
| 第一轮批量渲染 | 995.225秒 | 1060.470秒 | 单轮增加约7%，没有出现同量级翻倍 |

“正式批次前准备增加”与“正式批次执行增加”合计为41分21秒，约占44分40秒增量的93%。这是按用户时间记录计算的归属，不是对每一分钟内部活动的精确归因。

因此，第一优先级不是设法让每帧渲染快一点，而是让不该发生的试作门槛和整批返工不再发生。假设只把每次渲染提速，却仍把同一份输入做两轮，错误路径仍然存在；反过来，先删除重复工作，不要求改变机器配置就能验证行为是否正确。

参考库在1.3.0已经接入；1.4.0新增的不是只有参考资料，还有强制试作及设计关联检查。不能把“新版本更慢”直接推成“参考库太大”。同样，上一版未发现候选案例检索调用，也不能解释成参考库使用充分且完全没有成本。[H1]

### 0.3 两条实际失败链路，比“慢”这个结论更重要

**链路一：把低成本可发现的问题放进高成本试错。**

```text
正式批次要求先有当前版本的代表段视频
    ↓
同一约15.47秒段落完整导出
    ↓
查看图片后发现区域高度、结构层级等问题
    ↓
修改，再完整导出，再观察
    ↓
同一代表段累计三次成功试作，另有失败与修复
```

历史记录支持三次成功试作，并不支持“三次全都毫无价值”的结论。连续运动检查本身有价值；不合理之处是把完整视频设为统一必交凭据，使静态构图、输入错误等也通过昂贵路径暴露。按用户已确认方向，本轮取消这项统一门槛，不重新包装成强制静帧门槛。[H1][C1][C6]

**链路二：把补记录当成改画面。**

```text
漏写 visualDesign
    ↓
渲染前未发现，18条视频先完成
    ↓
合片时才要求补设计索引
    ↓
记录进入正式时间轴、生成源码和全部分镜参数
    ↓
整批版本与分镜内容摘要一起变化
    ↓
18条再次生成
```

两个正式批次都没有缓存复用；用户比较发现其中17条MP4的SHA256相同。这个结果支持“大量重复生成”的判断，却不证明画面质量合格，也不能把剩余一条未经解释的差异说成不存在。[H1]

真正要改的不是“下次别漏写”这一句话，而是让资料完整性在昂贵执行之前被确认，并让非执行记录不会污染媒体身份。

### 0.4 为什么不能仅凭这次记录给出更强结论

用户记录了当时调查到的服务器规模和资源上限，但没有完整历史资源曲线。不能据此断言运行时CPU一定闲置、一定被限流，或并发翻倍就能提速一倍。两版的声音长度和画面工程也不相同，不能把单轮多出的约一分钟直接认定为性能回退。[H1]

相反，“检查要求出现在哪个入口”“什么字段进入缓存键”“默认生成哪些证据”可以用固定提交的代码确认。本方案把这类可证明的结构问题优先改掉，剩余性能问题再用固定工程测量。

### 0.5 本文后续每项优化遵循的判断方式

先问这项工作是创作、实际制作、记录整理，还是验证；再问它依赖哪些已经存在的信息；最后才决定把它前置、复用、局部重做，还是继续完整执行。

由此得到三条边界：**补说明不自动重做媒体；改真实画面不能靠补说明放行；旧技术事实可以在可信条件下复用，但新的语义预期必须重新核对。** 后面的文件结构、缓存键和检查上下文都是为这三条边界服务，不是为了增加新的流程层级。

## 1. 结论：先消除错误返工，再优化剩余执行

原分析的优先级成立：不要先提高并发，更不要靠减少正文设计、简化动效、降低输出规格或取消终检来换速度。

但实施不能停在“取消试作、提前校验、忽略 visualDesign”三个口号上。当前代码存在多层耦合：

1. 正式批次直接依赖试作视频及其版本；Skill 和 Worker 提示词也要求先预览。
2. 设计完整性检查与真实成片检查混在同一函数里，无法原样提前执行。
3. 每个分镜的缓存身份绑定整个批次版本、完整时间轴和整个工程。
4. 财经时间轴派生器把全部时间轴写入源码，又复制进每条分镜的 props。
5. 默认取证只提取首、中、尾，而终检要求更多语义和动作边界，工具与验收不匹配。
6. 合片和终检会重复执行媒体验证；现有 Skill 还保留了可能诱发重复调用的分步交付示例。

这些修改应作为**同一项制作效率优化**联合设计、开发和验收，而不是拆成多个需要分别启用或分别确认的产品方案。

整体思路是：在创作和实现过程中形成必要设计记录及执行数据；渲染入口直接消费完整、确定的执行数据，不要求另交样片；媒体复用依据实际制作内容，而不是说明文字或整批管理版本；正式视频生成后由工具准备审片材料，再由同一个 Render 审看，最后经统一交付入口合片和终检。

这里有先后依赖，但没有多套工作流。例如，必须先明确哪些数据会影响画面，才能安全地定义缓存内容键；必须共用审片位置规则，工具才能一次准备好当前已知的截图。这些都是同一优化内部的工程依赖，不需要用户分别下单，也不代表生产任务按几个开发包运行。

调参同样属于本次优化的验证范围，但具体并发值由固定工程测试决定，不先承诺必须加到某个数值。正常任务不增加性能试作步骤。

### 1.1 为什么不是回退到旧版制作方式

1.3.0更快，并不代表那次动效、参考应用和视觉表现已达到目标。若直接恢复“少设计、填内置组件、少看过程”的做法，可能只恢复速度，却把本轮真正想改进的作品质量一并退回去。[H1]

本方案保留完整导演指令、主体造型、素材与动效结合、实际配音校准和成片观察；删除或改造的是把这些工作变成反复导出、补表返工的路径。创作时间可能因题材而波动，但补一项说明不应天然消耗另一轮整片生成。

### 1.2 正常制作、工具规则与开发安排要分开阅读

**正常制作**回答用户提交之后怎样得到视频，主线是创作、渲染、审片和交付。

**工具规则**回答程序怎样校验输入、固定版本、复用媒体、准备审片材料和完成终检。这些规则在正常调用内执行，不另设人工审批，也不让 Render 每一步先写一份“通过证明”。

**开发安排**回答要协调修改哪些文件、有哪些数据依赖以及怎样验证整体效果。它不是视频制作流程的一部分。

文末附录保留异常发生时的恢复规则。正常任务不会先制造缺漏、再补记录、再取图；制作资料应在创作时形成，审片材料应由工具根据当前已知需求准备。只有真实发生遗漏、追加观察或制作问题时，才涉及附录中的处理。

## 2. 固定提交核对发现的代码问题

### 2.1 “正式版本”的身份被同时当作“媒体内容”的身份

`render_batch.inputs()` 收集整个工程、全部分镜 props、完整时间轴摘要、依赖、浏览器和工具摘要。`freeze_batch()` 再用包括 run、entry、scenes、inputs 的整个合同生成 `manifest.version`。[C1]

`stage_media.render_scene()` 的分镜 fingerprint 又包括：

```text
整个 project 的指纹
当前 props（当前财经模板中又含全部 timeline）
完整 timelineHash
confirmedPlanSha256
当前帧数、规格、依赖、工具
batchVersion
```

因此，即使绘制组件没有改，某一个分镜参数变化也可以先改变整批版本，再让其他分镜的 fingerprint 全部变化。[C2]

这里应区分两个问题：

- 新批次是否属于当前任务、是否按当前确认稿执行：这是版本与授权一致性。
- 某条旧 MP4 是否仍由完全相同的制作输入生成：这是媒体可复用性。

两者都要检查，但不能用同一个哈希承担两种职责。

### 2.2 不只是 visualDesign 进入了 props，它还被写进源码

`finance_timeline.derive_timeline()` 读取正式时间轴，进行坐标别名转换、移除音频溯源字段，然后把剩余整份对象写入 `src/timeline.ts`；每条 props 又带有 `scene` 和完整 `timeline`。[C3]

当前 `project_fingerprint()` 除 `node_modules`、`.git` 外基本遍历项目文件。因此设计记录只要经派生进入源码，或者直接放进工程目录，也可能改变整个工程摘要。[C2]

这意味着仅从 `timelineHash` 中忽略 visualDesign 不够：源码摘要、props 和 batchVersion 仍会变化。更重要的是，如果组件实际读取这个字段，忽略它还会错误复用旧视频。

### 2.3 不能把 validate_delivery 整体移到渲染前

`validate_narration_review()` 前半部分核对时间轴、发言文本、设计覆盖；后半部分核对实际审片记录、MP4 证据和被观察的帧。[C2]

渲染前不存在这些 MP4 和观察结果。直接提前调用整套交付检查，只会制造新的“必须先有视频才能开始渲染”循环。

正确做法是按依赖拆开检查函数，而不是简单移动调用位置。

### 2.4 当前自动证据不足以满足自己的最终检查

`extract_frames()` 固定提取 `0 / frames//2 / frames-1`。但是 `validate_narration_review()` 还要求讲解区间两端，以及变化过程的动作前、开始、中间、结束前和结束后位置。[C2]

所以即使模型认真执行默认工具，也不能仅凭默认输出满足全部证据要求。应让工具知道本次需要哪些证据，而不是让模型在末尾发现缺图后手工补命令。

目录里“有 80 张图”不是优化或验收指标。真正应统计的是当前清单引用的有效图片、覆盖的检查项和缺失项；目录还可能含历史版本、重复图片或未被引用图片。

### 2.5 视频缓存命中后，仍可能重复做很多检查工作

当前 MP4 缓存命中分支仍调用 `validate_mp4()` 和 `extract_frames()`。`validate_mp4()` 中既有 `ffprobe -count_frames`，又有完整 FFmpeg 解码；交付验证还会逐个证据帧调用 `frame_rgb()`。[C2]

这不意味着应该取消这些检查，而意味着“视频复用”“技术检查复用”“图片复用”是不同的缓存层，不能只看 `reused=true` 就认为后续没有成本。

### 2.6 现有工具已经有一些优化，不应重复建设

批次已经共享 bundle、以长镜头优先派发并保留确认顺序；媒体执行已经保留无声画面和 PCM 供部分失败恢复；合片已经使用视频流复制、原混音 PCM 拼接并最后编码 AAC。[C1][C2]

因此不建议本轮先新增分布式队列、整套媒体 DAG、共享浏览器池或重写合片引擎。先修复现有机制的边界即可。

### 2.7 用一次“补设计说明”解释四层缓存耦合

假设只为“五层结构”补充“应用层最后形成对照”的说明，组件、素材和动作时间没有变化。这是说明当前代码可能行为的例子，不是声称本轮又执行了一次任务。

第一层，正式 `timeline.json` 的文件字节变化，`timelineHash` 变化。

第二层，派生器把整份数据写入 `src/timeline.ts`。于是源码文件变化，整个 `project_fingerprint` 变化。

第三层，每条分镜的 `props.timeline` 都带着全片数据，其他分镜也携带了这项说明变化。

第四层，批次冻结合同的输入变化，`manifest.version` 变化；每条分镜又把这个整体版本放进自己的 fingerprint。[C1][C2][C3]

所以，单独从 `timelineHash` 中排除该字段，只堵住了第一层；另外三层仍可能使缓存失效。反过来，四处都粗暴排除却不检查组件能否实际读取该字段，又可能错误复用真正已经变化的画面。

**这里的根因不是哈希算法慢，而是哈希输入的职责划分错了。** 先定义哪些数据真正决定输出、哪些只负责管理与说明，再计算各自的身份，才有安全的复用基础。

### 2.8 批次目录名不等于批次内容版本

需要特别澄清：当前 `manifest.version` 来自冻结合同摘要，不是直接由 `approved_v2` 这样的目录名生成。仅换目录名、保持合同完全一致，不一定改变版本；真正的问题是某个输入变化会进入整批合同，再经 `batchVersion` 传到所有分镜。[C1][C2]

后文“换批次可复用”的意思是：一次新的组织、重试或修订不应仅因整体管理身份变化就禁止复用未变媒体。不能把问题简化成“缓存键里放了一个批次名字”。

<a id="section-3"></a>

## 3. 正常制作流程：一条主线，不增加补漏阶段

```text
Analysis → 网页确认
    ↓
同一个 Render 连贯制作：
理解任务与模板 → 设计画面和动效 → 配音实测与时序校准 → 实现
    ↓
正式批量渲染
    ↓
审看正式作品
    ↓
统一交付：合片、最终检查、网页回传
```

这是正常路径，不画“缺漏／通过”或“补记录／重做”等异常分支。设计可以根据实测配音校准，这个概括也不要求所有创作动作严格串行或一次定死。

**正式批量渲染内部**，工具完成必要输入检查、版本固定、有效媒体复用和新视频生成。当前 `freeze-batch` 与 `render-batch` 的内部调用关系按第4—6章改造；它们不是新业务阶段，也不要求用户再次确认或先上传试作视频。字段、引用和范围的检查仍然执行，只是不再单列为一个审批式制作环节。

**审看正式作品时**，工具按当前已知的口播和动作位置，从真实视频准备截图等审片材料；Render 实际查看画面、运动、声音及设计落实情况。自动生成图片不等于已经看过。这里“审片材料”对应代码中的 `evidence` 等数据，并不是另一种需要用户提交的资料。

**统一交付内部**，工具合片、核对最终媒体和当前交付要求，并复用仍可信的技术检查结果。同一个 Render 负责完成制作和审看，不增加“设计 Agent、试作 Agent、整片 Agent”，也不由程序再分三轮派单。

设计记录随设计和实现形成，而不是视频做完之后专门补一遍。工具在正常渲染调用中检查这些现有资料，不要求模型额外生成一份渲染前“已观察／已通过”的报告。

发生实际错误时仍须处理；正常图不展开异常，不意味着删除错误处理。集中报错、从原视频追加审片材料、只重做真正受影响内容的规则见附录。

`render_batch.validate_preflight()` 是待取消的强制样片检查；`stage_media.preflight()` 是环境能力检查，检查 Node、浏览器、编码器和依赖版本，**不能一起删除**。[C1][C2]

### 3.1 为什么仍然由同一个 Render 连贯完成

本次发现的重复工作，并不是因为缺少一个专门做设计的Agent，而是同一执行阶段中的工具门槛、数据派生和恢复路径不匹配。增加设计、试作、整片三个代理不会自动改变这些规则；反而需要额外交接版本、声音边界、修改范围和审片结论。

所以优先在同一个Render内部修正工具协议。创作理解和修订上下文继续连贯，确定性资料由程序检查，真实作品由Render观察。这比先改代理拓扑更直接地对应已确认的故障原因。

### 3.2 取消强制试作的收益与代价必须同时写清

收益是不用为了获得制作通行证而先反复导出一段完整视频。代价是部分只有在运动过程中才显现的问题，可能更晚在正式分镜里暴露。因此取消门槛后，仍要允许按需查看静帧或局部过程，并保留正式成片修复。

但不能在别处写“所有问题都必须先用预览证明解决”，否则实际流程又回到强制试作。应区分：已经明确的错误必须修复；对效果存在不确定性时，Render选择是否使用低成本探索；没有固定的样片文件作为进入正式批次的必交凭据。

这也解释了为什么缓存和局部恢复需要继续改：取消前置样片后，正式成片修订更应避免牵连无关分镜。两项优化配合，才能减少试错总成本，而不是只把工作从前面挪到后面。

<a id="section-4"></a>

## 4. 渲染入口：将必要输入校验内置于正式制作

**为什么要先拆检查，再移动调用。**

渲染前已经存在确认稿、实际音频、设计、源码和参数；渲染后才存在真实MP4、由该MP4取得的图片和实际观察。这两个时间点能回答的问题不同。

“有没有覆盖u021”“字幕是否越界”只需要前一组数据；“动作是否真的发生”“截图是否来自最终视频”必须依赖后一组数据。把两种问题放在一个函数里，调用早了会要求尚不存在的媒体，调用晚了又让可提前发现的缺项拖到成片之后。[C2]

因此并不是新增两次完整审核，而是把同一套职责按数据依赖拆开：能确定的先查，必须看到作品的后查。前置检查失败时，只修资料或工程；后置检查失败时，根据错误所在层选择补证据还是改媒体。

**为什么不只在Skill里补一句“记得先写齐”。**

Skill指导模型如何工作，但不能保证每次都没有遗漏。本次正是“有要求、没在昂贵执行之前落实”的例子。正式入口必须承担最基本的确定性核验，否则换一次模型上下文或模板后，同样的返工仍可能重现。这里让程序检查字段和引用，不让程序替代导演判断。

### 4.1 按检查依赖拆分函数

以下函数名为建议新增接口，不是当前已有接口：

```python
validate_production_inputs(request, timeline, design, runtime_inputs)
validate_review_evidence(request, delivery_manifest, design, review)
validate_delivery(..., validation_context=None)
```

第一项不要求 `wholeVideo`、分镜 MP4、`viewedFrames` 或 `passed`。第二项必须读取真实成片和真实观察记录。第三项仍保留最终交付总入口。

建议将纯字段与引用检查放进一个小型共用模块，例如 `tools/production_contract.py`，供 `render_batch.py`、`stage_media.py` 调用。不要复制两份规则，也不要把新的校验器写成又一个 Agent。

### 4.2 渲染前检查范围

| 类别 | 应检查 | 不能据此断言 |
| --- | --- | --- |
| 确认稿 | sceneId、顺序、文本拼接与当前确认稿一致 | 文案具有吸引力 |
| 音频时间轴 | 实测音频摘要、样本覆盖、句级边界、字幕关系、片尾顺序 | 所有语义接点都准确 |
| 设计索引 | 设计 ID 唯一、引用有效、覆盖完整、模式有效、说明及实现引用存在 | 所有动画已经兑现、画面好看 |
| 执行输入 | Composition 声明、必需参数类型、frames/fps/尺寸、资源存在与路径范围 | 动态注册的所有组件都必然运行成功 |
| 工程 | 使用环境已有能力检查语法、类型或构建错误 | 没有布局溢出和视觉遮挡 |
| 取证计划 | 检查区间与动作引用有效、帧位置合法 | 这些图片已经生成或已经看过 |

不能静态确定的 Composition 信息，仍在实际 `selectComposition()` 阶段核验；不要把这类运行时核验伪装为“不启动浏览器的检查”。确定的字段缺漏必须先于打包和浏览器启动返回。

### 4.3 在两个入口执行同一套检查

`freeze_batch()` 在昂贵指纹扫描和冻结写入前执行一次；`render_batch()` 在派发前核对当前输入与冻结结果，防止冻结后被修改。缓存命中也不能跳过当前确认稿、授权、记录关联及当前交付要求检查。

资料校验结果可以按当前输入版本复用，但不能接受模型自行填的“已通过”。第一次实施可只在可信工具本次执行内复用，不增加跨任务校验缓存。

### 4.4 如何验证渲染入口的行为

最直接的测试不是整片突然快了多少，而是故意提交一个缺设计索引的任务，确认工具在启动任何分镜浏览器渲染之前返回缺漏。补齐后，不上传样片也能开始正式制作。

这是整体优化的一项针对性测试，不是独立产品包的交付终点。完整验收还须覆盖正常制作、说明修订、媒体复用、审片及交付的联动行为。集中报错的字段示例与异常恢复理由保存在文末附录，不作为正常制作的必做步骤。

## 5. 数据职责：让设计记录与实际渲染输入分离

**为什么需要分离记录，而不是删掉记录要求。**

设计索引有实际用途：它把“准备怎么表现”“由哪段实现负责”和“成片检查了什么”联系起来。删除整个索引虽然可能减少填表，却也失去定位未实现设计的依据。因此本方案保留它，只改变它存放的位置和进入执行的方式。

这里必须区分三种变化：

| 变化的性质 | 例子 | 正确处理 |
| --- | --- | --- |
| 对已有事实补充说明 | 补写“能源层在对应口播处亮起”，原视频已经如此 | 媒体不变；核对记录确实对应原视频 |
| 改变设计预期，但尚未改实现 | 新要求“应用层必须形成强烈反差” | 媒体可暂时复用来重新审阅，但不能直接继承通过结论 |
| 改变实际执行 | 改颜色、运动范围、字幕、音效、动作起点或素材 | 渲染输入变化，按影响范围重新生成 |

同样是编辑description，可能只是补写，也可能改变了验收预期。程序可以判断说明与媒体的版本关系，却不能仅靠字段名确定所有语义。最终必须保留设计与作品的核对。

**因此，“设计文件不进入媒体哈希”不等于“设计变了什么都不用做”。它只意味着不要先自动重做视频；应先判断原视频是否已经满足当前设计。**

### 5.1 推荐文件职责

```text
render/<runId>/
  direction.json           全片方向与模板边界
  chapters/.../brief.json   详细导演、美术与连续演出指令
  design.json              轻量设计执行索引，引用 brief 和实际事件
  timeline.json            实际发言、字幕、视觉事件、声音与片尾时间轴
  runtime/                 可信适配器生成的实际渲染参数
  review-plan.json         工具派生的待检查位置，不含“已观察/已通过”
  review.json              真实成片产生并被查看后的观察结论
  batches/...              不可变批次与结果

project/                   只保留实际代码、样式及渲染所需资源
```

这是职责分离，不要求模型反复写同一份设计。完整演出继续只写在章节 brief；design 只是将设计、实现和审片关联起来的轻量索引。

`review-plan.json` 由工具从已知的发言边界、视觉事件及设计引用派生，不再让模型手工复抄所有帧号。

### 5.2 visualDesign 保留语义，但移出派生执行对象

可以保留现有设计 ID、utteranceIds、mode、description 和 implementation，放在 `design.json` 的对应镜头下。

建议示例：

```json
{
  "schemaVersion": 2,
  "scenes": {
    "scene_007": {
      "briefRef": "chapters/chapter_02/brief.json",
      "designs": [
        {
          "id": "five_layers",
          "utteranceIds": ["u021", "u022", "u023"],
          "mode": "change",
          "description": "各层随对应口播依次建立，最后让应用层形成明显对照",
          "implementation": {
            "path": "project/src/FiveLayers.tsx",
            "export": "FiveLayers"
          },
          "eventRefs": ["energy_focus", "chip_focus", "application_contrast"]
        }
      ]
    }
  }
}
```

`eventRefs` 引用真正被组件消费的执行事件，或由模板可信适配器解析的真实动作窗口；不能仅在 design 中新增一套假时间。组件已经使用实际 utterance 边界推导动作时，可以提供绑定这些执行表达式的规范化动作记录，不必为接入强行重写全部动画代码。

创作指令可以继续用相对秒数描述节奏，精确执行和技术核验再依据当前实测声音转换为帧；不能用固定帧数要求延长口播或填满空白。

### 5.3 必须修改派生器和相等性校验

`finance_timeline.derive_timeline()` 不能再把未知字段直接透传进 TS 和 props，应从当前模板声明的执行字段构造投影。纯设计说明只归入 design，不进入绘制参数。

`stage_media.fixed_ending_context()` 当前以正式时间轴派生的完整对象与 props 比较。改变派生对象后，它必须调用同一投影逻辑，否则会把合法的新 props 报为 `TIMELINE_STALE`。`scene_audio_contract()` 仍需保留 BGM 全局起点、音频来源和片尾边界等实际声音依赖。[C2][C3]

新增模板执行字段应更新模板适配声明；不能在通用层静默丢弃未知字段，否则可能丢掉真实画面参数。无法确认依赖的旧模板保留保守复用模式，并明确标识模式。

### 5.4 “文件分开”不是隔离的充分条件

至少应满足：渲染 props 不含设计/审片字段；源码和 public 不包含其副本；构建和运行不能另行读取这些记录并决定输出。

当前内层 bwrap 命令中的 `--ro-bind / /` 只保证该视图只读，不自动禁止读取说明目录；`native` 是否受外层隔离，还需实施时核实 Worker 的实际启动边界。[C1][C2]

因此，安全启用“忽略记录变化”的前提，是让支持该契约的模板通过受控执行输入工作，并在构建导入/路径访问或挂载边界上阻止读取 design/review 等旁路文件。依赖、系统库和临时目录仍按现有授权开放，不开放未经固定的远程资源作为隐式渲染输入。无法确认此条件时，应继续保守失效，而不是只在哈希函数中删除字段。

### 5.5 为什么派生和核验必须使用同一套执行字段定义

把时间轴投影成渲染参数时，不能简单写一个通用过滤器，遇到不认识的字段就丢掉。因为某个新模板可能把该字段用于真实动画，静默删除会让工程成功导出一个错误结果。

应由所选模板的可信适配规则明确哪些数据属于执行输入。派生器按照该规则生成参数，渲染前核验按照同一规则比较参数与正式时间轴。不能一边按新字段集合生成，一边仍拿旧完整对象逐字比较；否则会把合法输入误报为版本过期。[C2][C3]

设计说明从现有 `visualDesign` 迁出时，也应明确处理旧schema。旧任务不能在无人知晓的情况下被套上新规则；无法确认某模板从未消费该字段的，暂不启用排除规则。

### 5.6 从“文件挪开了”到“确实不影响画面”，还差一步

假设design.json已经放到project目录外，但组件或构建脚本通过相对路径读取它，再据此决定颜色。此时修改设计文件仍会改变输出；仅因为它不在project里就忽略摘要，缓存就是错误的。

所以应同时检查两条输入路径：显式props，以及源码导入、资源读取等旁路。只读挂载解决“能否修改”，并不自动解决“能否读取”。能读取并影响画面的内容，就属于执行输入，必须被固定和计入身份；纯记录应不能通过旁路参与画面生成。[C1][C2]

这不要求本轮建设新的通用安全平台。先针对当前支持的模板和现有构建/沙箱边界建立明确契约；无法证明边界的旧模式继续保守失效。不能一边保留任意旁路读取，一边宣传“所有说明修改都能安全复用”。

### 5.7 为什么说明复用与局部媒体复用需要区分验证

本次最直接的异常是“只补设计记录，18条都重做”。完成记录分离和输入边界后，这类修订不再改变实际project、执行时间轴和props，即使缓存仍对真正的全局变化保守失效，也可以不重做这18条。

“改第7镜独立参数，只重做第7镜”还需要第6章处理整批版本和全片数据耦合。这是同一套复用规则的两个不同验证场景，应一起实现目标范围内的联动，但分别证明正确性。只证明说明复用，不能宣称局部媒体复用已经完成；分别测试也不意味着拆成两个产品或两次用户任务。

<a id="section-6"></a>

## 6. 媒体复用：按实际制作内容判断，不与整批管理版本捆绑

**为什么要区分“属于哪一轮”与“实际做了什么”。**

一个新的批次可以重新组织任务、修复其中一镜、重新绑定当前设计记录，而不改变另外17条视频的制作输入。管理系统需要知道这些产物被哪一轮采用；渲染器则需要知道它们是否必须重新生成。两种信息关联即可，不应互相替代。

可以类比一次文档修订：文档版本更新，不代表每张未变插图都需要重新绘制；但旧插图仍要确认来源、内容和当前使用要求。视频缓存同理，复用的是满足当前执行合同的媒体字节，不是直接复用上一轮“整个任务已通过”的状态。

当前代码把batchVersion同时当成媒体输入的一部分，正是这两个问题混在一起。[C1][C2] 以下几种身份不是为了增加版本管理层，而是让不同变化只使真正相关的结果失效。

### 6.1 建议区分的几个身份

不需要引入通用依赖图系统，用明确数据结构就能完成第一版。

| 身份 | 用途 | 典型内容 |
| --- | --- | --- |
| batchVersion | 本轮管理、冻结、归属和顺序 | run、分镜清单、当前版本与执行输入引用 |
| renderInputKey | 决定某镜的媒体是否可复用 | 代码与运行时、实际 props、相关全局上下文、素材内容、帧长、输出与编码设置 |
| reviewRevision | 当前设计与观察是否对应 | design 摘要、实际媒体摘要、观察记录和检查规则 |
| assemblyKey | 当前整片是否仍对应当前分镜集合 | 有序分镜视频摘要、原混音摘要、帧数、合片设置 |

批次名称、attemptId 和 reviewRevision 不应进入媒体内容键；但任务归属、确认版本和授权仍应在可信入口独立核对。第一版只做同任务同 run 的复用，不扩展为跨用户、跨任务缓存。

示意：

```text
sceneKey = H(
    cacheSchemaVersion,
    renderSourceAndRuntimeIdentity,
    compositionId,
    runtimePropsForThisScene,
    declaredGlobalContext,
    relevantAssetContentHashes,
    frameCount,
    outputAndEncoderSettings
)
```

`renderSourceAndRuntimeIdentity` 必须覆盖实际影响输出的代码、共享依赖、浏览器和编码环境；不能从 batchVersion 移除依赖后又遗漏浏览器、共享 lib 等变化。第一版仍可对渲染相关工具文件做保守整体摘要，不必先手工维护脆弱的“某函数版本号”。

### 6.2 同一复用机制要覆盖说明修订与局部内容修订

**第一层：纯记录修订复用。** 完成 sidecar 与访问隔离后，修改 description、observed 等不改变 project、timeline 执行内容或 props，因此可复用原媒体。此时即使还没有消除所有全局输入耦合，也能解决本次“补设计记录导致整批重做”的核心问题。

**第二层：局部执行参数修订复用。** 将 batchVersion 从分镜媒体键中剥离还不够，需要继续移除每个 props 中不必要的整份时间轴，并停止把全片数据固化成所有分镜共同依赖的 `src/timeline.ts`。

对于支持新输入契约的模板，源码保持稳定，实际内容经外部 props 注入；本镜收到自身数据和明确使用的全局字段。当前仍直接依赖完整时间轴的模板先维持保守模式。

### 6.3 全局依赖不能为了命中缓存而省略

全局进度条可能依赖总帧数和章节位置；章节导航可能依赖全片标签；BGM 可能依赖当前镜头的全局起点；片尾保持区间也可能影响末镜。

因此：

| 修改 | 合理行为 |
| --- | --- |
| 只改设计说明或观察文字 | 媒体复用；重核相关设计/审片对应关系 |
| 只缺某些成片截图 | 从当前 MP4 补取证；不启动浏览器 |
| 只改一镜独立数据，代码和它镜全局输入不变 | 新输入契约下仅该镜失效 |
| 改共享组件、字体或公共样式 | 第一版允许相关全批保守失效 |
| 前镜延长，使后镜 BGM 起点或进度条变化 | 重做实际依赖发生变化的镜头；可能不止一镜 |
| 修改实际音效、音频文件或动作窗口 | 受影响镜头失效；不能当作说明修订 |
| 换 batch ID，但实际输入相同 | 可复用全部有效分镜 |
| 缓存媒体或混音被改坏 | 拒绝复用，保留诊断并按恢复规则处理 |

“改了 scene_007.tsx 只重做 scene_007”不是第一版承诺。若该文件属于共享 bundle，而系统无法安全判断其影响范围，继续整批失效是可接受的。没有必要为此先建设复杂的自动源码依赖分析。

### 6.4 缓存命中要生成当前交付的关联信息

媒体字节可以复用，但不能把旧批次的 manifest 原样登记为当前结果。建议当前结果记录：

```text
currentBatchVersion
renderInputKey
outputSha256
mixSha256
cachedFrom（来源批次/内容键）
当前检查和设计记录关联
```

可信工具核实来源对象、摘要、规格和当前授权后生成这些字段，不能由模型换一个摘要宣称“新版本已通过”。

### 6.5 缓存层别一次拆得过细

当前 raw cache 已能复用无声画面和 PCM 来恢复部分封装失败，应先保留。第一轮不必强制拆成浏览器画面、音轨、片尾、转场等十几个缓存节点。

后续确有数据证明封装修复频繁，再把原始渲染键与封装键拆开。注意当前 raw 和最终输出使用相同 fingerprint，且该键含整个 `stage_media.py` 摘要；更改检查代码也可能使 raw 失效。这属于后续按职责拆模块的机会，不是本次必须先完成的重构。[C2]

### 6.6 “只改一镜”需要同时通过两道判断

第一道判断是**实际读取范围**：其他分镜是否读取了被改的数据？如果每条props仍然携带并允许读取全片timeline，就不能仅凭“我修改的是第7镜”认定其余17镜无关。

第二道判断是**真实依赖变化**：其他分镜虽然没有使用第7镜的局部标签，但是否使用全局总时长、章节进度或BGM起点？这些输入一旦变化，其他镜头也可能需要重做。

例如，只改第7镜某个局部图示的标签，在新模板契约下可以只影响第7镜。若第7镜延长一秒，则后续镜头的全局起点可能改变；存在全局音乐、进度条等依赖时，受影响镜头就不止一条。缓存应该如实报告这种原因，而不是把低命中率一律当成缺陷。

### 6.7 用三组对照解释内容键的边界

| 对照场景 | 为什么应该复用或失效 | 验收重点 |
| --- | --- | --- |
| 新建批次，实际执行合同相同 | 管理过程变化不等于媒体内容变化 | 复用来源可信，仍生成当前批次关联 |
| 保持素材路径，替换文件内容 | 路径相同不代表输入相同 | 必须按内容摘要失效 |
| 修改共享动画组件 | 无法证明其他镜头未使用它 | 第一版保守失效可以接受，不能为了命中率漏掉真实变化 |

同理，移除batchVersion后，原本由它间接覆盖的浏览器、共享lib或依赖信息必须进入正确的内容身份，不能一起丢掉。否则会出现“新环境生成结果可能不同，缓存却仍然命中”的新问题。[C1][C2]

第一版不追求任意源码修改都能精确追踪到一镜。支持本镜参数的独立复用，并对公共源码变化明确保守失效，已经能解决大量不必要的牵连；复杂源码依赖分析应由后续真实需求驱动。

### 6.8 为什么不能只看MP4摘要相同就说节省了渲染

历史案例中，17条MP4重新生成后字节仍然相同。这恰好说明“前后SHA256一致”可以证明内容一致，却不能证明过程没有重做。[H1]

因此测试必须同时记录内容键、缓存命中原因、新启动的浏览器渲染任务数、实际新渲染帧数与复用来源。纯记录修订的目标是这些昂贵执行没有发生，而不是重新跑完之后得到相同文件。

还要区分媒体复用和检查复用：旧视频可以不重做，但当前授权、确认稿、设计对应关系仍要核对；技术事实是否能复用，由第8章的可信边界决定。

<a id="section-7"></a>

## 7. 审片材料：从正式视频准备当前需要查看的内容

**为什么末尾补图不是单纯的模型粗心。**

如果默认工具只返回首、中、尾，而最终校验要求每个讲解区间和动作窗口的更多位置，那么“按默认工具做完”与“可以提交”之间天然存在缺口。每次靠模型回忆规则、补写取帧命令，会重复支付定位和解码成本。[C2]

因此需要前置的是“待查看位置的组织”，不是“视觉通过结论”。声音区间和执行事件在渲染前已经存在，可以用于列出待检查清单；成片是否满足预期，必须等真实媒体产生后观察。

取证计划也不应重新定义动画。动作起止必须来自组件实际消费的时间参数、真实utterance边界或可信适配器规范化结果；不能为了自动生成若干图片，再发明一份与代码无关的动作时间表。

### 7.1 先知道“该看哪里”，但不提前伪造“已经看过”

渲染前从实际口播窗口、实现事件和设计引用生成 `review-plan.json`。它只能包含待检查内容和位置，不包含 passed、observed、humanListeningPerformed 等已完成结论。

现有规则中，一个讲解区间需要区间首尾；change 还需要动作前、开始、中间、结束前和结束后。这些位置可以由同一个规则函数产生，并由最终验证器复用，避免工具和校验规则再次分叉。

### 7.2 每个视频汇总一次目标帧集合

```text
neededFrames(scene) = 去重排序(
    分镜首中尾
    + 讲解检查区间边界
    + 动作前中后及收束位置
    + 模板要求的字幕、转场与片尾风险位置
)
```

执行器把它传给扩展后的 `extract_frames(..., indices=...)`。正式 MP4 完成后一次解码选出所需位置，输出清单中保留原始帧号、视频摘要、图片摘要和用途。

FFmpeg 的 select 支持按帧序号表达式选择多帧，适合替代“每张图从头解码一次”。[E1] 应保留帧号映射、帧数验证和一致的缩放/色彩处理；不要用不精确的时间 seek 冒充原先的精确帧检查。

### 7.3 图像生成、图像观察和作品通过是三件事

工具可以自动生成 evidence，但不能自动把所有 evidence 帧号写成 viewedFrames，更不能自动填 passed=true。

审片仍由 Render 真实查看。需要判断连续运动时查看实际连续过程；只有静帧能力时记录限制，不声称已播放或已试听。抽帧完整性不等于动画连续性达标。

纯说明修订但实际设计预期变了，旧媒体仍可复用，相关语义结论却应重新核对，不能一并继承“已通过”。

### 7.4 补证据失败不应该启动新的渲染

新增图片或缺失图片的恢复路径直接读取已核验的 MP4。缓存视频命中后，也先核对已有图片的来源摘要和目标帧集合，只补缺项，不无条件重提首中尾。

证据应按媒体摘要分目录或版本化保存，避免同一个 `sceneId-frame.png` 在修订后覆盖旧证据造成混淆。

### 7.5 为什么取证规则要共用，而不是维护两套帧清单

最容易再次出错的实现是：提图函数里写一份“需要哪些帧”，交付校验里又写另一份。以后审片规则改了，生成工具没有同步，又会出现这次的末尾补证据。

应让生成工具和校验器调用同一个“所需位置”规则；生成工具负责输出，校验器负责确认输出来源、范围与观察记录。可以接受用户或Render补充新的风险位置，但必须先验证范围，并从当前有效媒体提取。

新发现的风险不可能全部提前枚举。因此“一次提齐”是一次提齐**已经知道的**要求，不是保证之后永不补图。追加证据时仍走当前MP4提取路径，而不是重新生成动画。

### 7.6 为什么图片数量不应该变成新的绩效目标

80张图片可能包含有效覆盖，也可能包含历史版本或重复证据。只追求张数变少，容易漏掉关键过程；只追求张数变多，又可能把同一件事看很多遍却没有发现问题。[H1]

更合理的指标是：当前有效媒体对应多少待检查项，已有证据覆盖多少，缺失多少，发生几次解码和补取，观察是否真实完成。对运动连续性有疑问时仍要检查连续片段，不能用“图片齐全”冒充连续运动已经验证。

<a id="section-8"></a>

## 8. 统一交付：减少重复检查，保留最终质量与一致性核验

**为什么保留终检，不代表相同媒体必须重复完整解码。**

合片前检查每条分镜，是为了不把错误素材拼进去；合片后检查整片，是为了确认拼接没有产生顺序、边界、声音和时长问题。这两种职责都必要。但同一条未改变的分镜，在一次交付里先后被两个入口读取，不意味着它的全部技术事实都必须重新计算。[C2][C4][C7]

例如，“这条摘要为X的MP4在规格Y下完整解码且帧数为N”是关于固定媒体的技术事实；“这段动画符合当前设计”是关于媒体和设计预期的关系。前者在文件、规格和规则不变时有复用基础；后者在设计说明变更后可能需要重新观察。

所以应缓存明确的技术检查项，而不是缓存整个 `validate_delivery()` 的“通过”结论。确认稿、授权、资源引用、设计对应及最终交付对象依然要按当前状态核对。

**为什么先做本次调用内复用。**

本次进程内由可信函数产生结果，来源较容易控制。若直接持久化一个“已通过JSON”，还要处理谁能写、能否被模型改、检查器版本是否一致、视频是否被替换等问题。本轮不必为减少重复解码再引入一套复杂的跨进程证明系统。

### 8.1 当前确实存在重复调用路径

`assemble()` 合片前调用 `validate_delivery()` 检查全部分镜；`task_io.complete_render()` 随后还会调用 `two_stage.validate()`，后者再次进入 `validate_delivery()`。制作 Skill 还列出手动 assemble、手动 validate，再通过 task_io 返回的路径。[C2][C4][C6][C7]

这证明存在重复验证的代码路径，但不能把用户记录的“交付 4分30秒”全部认作重复检查，更不能宣称其可以完整消除。具体收益需要计时。

### 8.2 优先统一 Worker 的交付入口

Worker 的正常完成路径只显式调用一次 `task_io.py render`。它已经会在缺少整片时调用 assemble，保留这个职责即可。

Skill 中将手动 assemble、validate 标为本地调试或特殊检查路径，不再将其描述为 Worker 交付的必做前置步骤。不要删除底层命令，它们仍有独立诊断用途。

### 8.3 第一版只做同一次交付进程内的可信复用

这是比新增持久化“已通过报告库”更简单的方案：

```text
complete_render()
    创建 ValidationContext
    ├─ assemble(..., context)
    │    分镜技术检查 → 保存本次可信结果
    │    合片 → 验证新整片
    └─ validate(..., context)
         再核对当前输入、文件摘要和规则
         复用相同键的分镜技术事实
         执行整片顺序、全局边界、音频拼接及最终设计关联检查
```

`ValidationContext` 只由可信函数写入，不接受模型提交的 `passed.json`。

缓存键按检查种类包含媒体内容摘要、相关混音摘要、预期规格、帧数、检查参数、校验器身份，以及必要的解码器环境信息。图片真实性检查还要绑定图片摘要、帧号和视频摘要。

同一次交付过程中应使用稳定文件或受保护快照，并在关键边界复核摘要，避免“检查时是 A，交付时变成 B”。如果文件或规则变了，对应缓存立即失效。

第一版不复用前一次进程的检查结果。以后要持久化，必须有可信写入位置与防伪/完整性边界，不能把任务内可手改的 JSON 当作验证凭据。

### 8.4 减少重复解码，不减少最终检查覆盖

将 `frame_rgb(path, index)` 的逐项调用替换为按视频聚合的取帧函数。整片所有分镜首尾位置一次收集，分镜证据校验也按视频收集。以解码后的同一份可信帧数据进行原规则比较。

`probe()` 当前无论调用目的都使用 `-count_frames`。[C2] 建议区分普通元数据查询与需要实测帧数的严格验证；真正检查 MP4 完整性时保留实测帧数及解码验证。FFprobe 将 count_frames 定义为逐流统计帧数，不能仅把它当作免费的文件头读取。[E2]

对 `audio_info()`、PCM 提取和音轨比较同样可做本次可信执行内的内容摘要缓存。一个镜头已完成的技术事实可以复用；整片拼接出来后产生的新风险仍要单独检查。

### 8.5 技术复用不应自动跳过新产生的整片风险

假设18条分镜都完成技术验证，随后合片生成一个新文件。这个新文件仍然可能出现顺序不对、全局边界异常、声音拼接错误或总长度不一致。分镜检查通过不能推出整片检查通过。

因此复用的边界是：不重复计算已有的、仍可信的分镜技术事实；新整片必须检查它新增的风险。最终“独立终检”指可信交付入口仍独立核对当前交付事实，而不是把Render写的passed当作结论，也不是要求每项已经验证的字节都机械解码两遍。

复用时仍要防止文件在检查和交付之间改变。执行中保留稳定对象或受保护快照，关键边界复核内容；上下文不接受任务工程自行写入的成功标记。合并入口时还应沿用现有锁顺序，避免嵌套获取同一非重入锁造成新的卡住。

### 8.6 为什么不能把合片的全部耗时都解释为重新编码

现有合片路径已经复制视频流，并对原混音PCM按镜头帧长处理后拼接、编码AAC。[C2] 因而“合片花了几分钟”不等于“整片画面又从头渲染了一遍”。其中还包含逐镜核验、音频处理、封装、整片校验等工作。

用户记录中的合片命令和最终交付命令时间，不能直接当作某个校验函数的时间，更不能全部作为可删除开销。应先拆分计时，再优化重复解码、重复取帧和重复入口调用；保留真正改变或验证新交付对象的必要步骤。

<a id="section-9"></a>

## 9. Skill 和提示词具体修改文案

**为什么工具修改之后，还必须系统性修改指令。**

即使代码已不阻止无样片的正式批次，Worker提示词仍可能要求“先预览代表段”，制作Skill的另一段仍可能要求“当前版本试作通过后才能导出”。模型继续按旧指令反复做样片，耗时并不会因为删除校验函数自动消失。[C6]

反过来，只改Skill而不改工具，模型会按新要求开始批次，然后被旧 `validate_preflight()` 拒绝。两种错配都会制造新的重试。

所以需要同时清理三类地方：主流程的必做步骤、示例命令体现的默认路径，以及错误恢复时“缺什么就补什么”的指令。环境能力检查与按需创作预览保留；强制代表段通行证与Worker正常交付的重复入口要求删除。

原有导演和美术要求不应借此缩短成“选组件、填文字”。本轮优化针对的是执行路径，不是撤回内容个性化、连续演出和真实素材配合的目标。

### 9.1 production-flow.md 的正常制作主线建议替换文字

> 在当前任务和模板范围内，由同一个 Render 连贯完成理解、设计、配音校准、实现、正式渲染和审片。详细演出随设计保存在章节 brief，设计索引与对应实现同步形成；实际声音、字幕、视觉事件及片尾时序保存在 timeline.json。不要等正式视频完成后再集中补写制作记录。
>
> 使用当前模板的可信适配器派生实际渲染参数，并经正式批量渲染入口完成制作。工具在冻结及派发过程中核对必要输入并固定版本；不要求先提交代表段视频、截图或“已观察”报告。纯设计及审片说明不进入绘图参数，也不能经旁路被组件消费；尚不支持该隔离的模板使用明确的保守模式。
>
> 正式分镜生成后，工具根据当前已知的审片位置准备真实视频的截图等材料。实际查看作品后记录观察，核对画面、连续变化和真实声音接点；不能将自动生成的图片直接登记为已查看。观察或试听能力的限制如实记录。
>
> 完成审片后，正常 Worker 交付统一调用 task_io.py render，由工具合片并执行最终检查，返回整片和全部确认分镜。手动 assemble、validate 保留诊断用途，不列为每次正常交付都必须重复调用的前置步骤。

**放入 Skill“失败、恢复与预算”部分的处理规则，不插入正常主流程：**

> 出现输入问题时，按照工具一次返回的可定位问题修正，再调用同一入口；不伪造通过记录，也不绕过预算。纯说明修订只更新记录并核对与当前作品的关系；增加或缺少审片图片时，从当前有效视频提取。实际代码、素材、声音或时序变化时，按当前有效输入重新冻结并重做真正受影响的媒体，保留仍有效的其他结果。未解决的实际制作问题不能靠补说明交付。

### 9.2 production-flow.md 必须同步清理的位置

不仅删除文末样片 JSON，还要检查“导演、美术制作”“主控编排与章节并行”“渲染前检查”“设计执行索引与批量制作前检查”等段落，移除正式制作必须先完成章节动态预览、必须提交 preflight-review 的指令。

保留按需创作预览和正式成片观察，但不得在另一个段落重新引入硬门槛。保留取消、租约、预算、源素材授权和最终质量要求。

### 9.3 prompts.ts 中 renderCreation 建议替换的核心段

> 由你连贯完成当前视频的设计和制作。章节 brief 写清主体、起态、连续变化、中途、真实口播接点与出口，再按设计实现，并依据实际配音校准时间。设计索引与实现同步形成，正式制作通过批量渲染入口进行，必要输入校验和版本固定由工具承担，不要求先提交代表段预览视频。正式分镜生成后，使用工具准备的真实审片材料查看作品、核对设计落实；完成后通过统一交付入口合片、终检并返回结果。异常恢复遵循 production-flow.md 对应章节，不把补记录或补图当成正常制作阶段。

`renderDelivery` 保留既有并发配置、前台等待、任务锁、完整交付和回调规则，强调正常交付由 `task_io.py render` 统一完成。

### 9.4 不修改的创作要求

不压缩导演指令为组件名称，不取消素材与动效结合，不要求优先填基础图解，不降低重要连续过程的设计深度，也不把所有 mode 改成 hold 来通过校验。

### 9.5 为什么必须检查“隐藏在其他段落的旧要求”

当前制作流程不是只在一个小节提到预览，还在导演/美术深化、章节验收、渲染前检查和文末版本记录中描述相关要求。[C6] 只删除最后的preflight-review示例，前文仍可能把动态预览作为必经步骤。

修改后应全文检查“代表段”“preflight-review”“正式批次前”“先预览”“章节动态预览”等表述的实际语义，而不是把所有包含preview的句子一律删掉。测试代码、历史验收记录可以保留旧语义，但应明确为历史或回归材料，不能继续成为当前执行指令。

同样，正常交付示例应以一次 `task_io.py render` 为主；手动assemble和validate保留调试用途，避免模型把三个命令连续执行当作更保险的标准流程。

## 10. 性能测量：用固定工程确定剩余优化空间

**为什么并发放在后面，而不是认为并发没有价值。**

当前主要增量来自额外制作门槛和多一轮正式批次，这有明确记录。增加并发只能让这些额外执行更快，不能证明它们应该发生。先修路径，可以先得到行为上的确定改善；再优化剩余的单轮成本，收益也更容易解释。[H1]

并发还有两个不同层次：同时渲染几条分镜，以及每条分镜内部同时处理多少帧。它们对浏览器数量、内存、线程和任务竞争的影响不同，不能只看到56个逻辑CPU就直接把任一数值拉满。用户记录的12核、16GB上限还需要结合实际任务边界和运行采样理解，不能把物理机器规格等同于某个任务随时可用的资源。[H1][C1][C2][C5]

这里采用“固定工程—测量—小步调整”的思路，而不是在正常用户制作中重新加入性能试作。所有配置必须通过Worker授权边界生效，不能让模型自行提高资源上限。

### 10.1 先补足现有指标

当前批次已有 slots、bundleSeconds、sceneSeconds 和部分资源指标；分镜已有 renderSeconds、mixAndValidationSeconds、evidenceSeconds。优先扩展这些结构，不建设新监控平台。[C1][C2]

建议记录：

```text
生产准备墙钟、必需工具调用区间
输入检查、输入指纹扫描、bundle
浏览器启动、Composition 解析、帧渲染、编码
封装、实际技术验证、抽帧、观察与修订
合片、终检、回传
每镜 renderInputKey、cacheHit、cacheMissReason、复用来源
本次启动的浏览器渲染任务数、实际新生成帧数
```

“模型活动时间”可按可观测工具事件粗分；不要将工具之外的所有等待都精确归因为模型推理。

Remotion 的 onStart/onProgress 提供实际并发、渲染/编码进度等细分信息，接入前按服务器锁定版本确认支持字段。[E3] 各耗时存在重叠时，不能简单相加代替墙钟。

### 10.2 CPU、内存和 PID 应按实际任务边界观测

当前 cgroup 采样主要覆盖 PID、memory 和 PID 拒绝事件，不能代替 CPU 节流测量。建议由批次协调器统一采样 CPU 使用与限制、节流计数、内存/OOM、PID 上限事件及可见的 I/O 信息。各并发子镜看到的可能是同一个 cgroup，不能把这些值相加当作每镜独立占用。[C2]

服务器总核数和当前配置只能作为测试条件；没有历史数据，不推断旧任务当时一定闲置或受限。

### 10.3 并发实验分两个维度

当前 `render_scene.cjs` 写死 `concurrency: 1`，外层最多 5 槽。[C1][C5] 建议在受控部署配置中新增可校验的帧并发设置，模型不能自行绕过任务资源边界。

示例实验组合（不是上线推荐值）：

| 分镜槽数 | 每镜帧并发 | 用途 |
| --- | --- | --- |
| 5 | 1 | 当前基线 |
| 3 | 2 | 比较少浏览器、较多镜内并行 |
| 4 | 2 | 中等负载组合 |
| 5 | 2 | 仅在资源观测允许时继续 |

两者乘积只是配置规模的近似描述，不等于 CPU 使用核数；浏览器、视频解码和编码还会产生其他进程或线程。Remotion 官方也指出并发既可能提速也可能变慢，应使用 benchmark 寻找适合当前工程的值。[E4]

高并发前应回归同一帧重复渲染是否一致、动画是否依赖墙钟/随机数/上一帧副作用、字体和资源是否等待就绪。Remotion 强调动画应由 useCurrentFrame 驱动，单并发不是非确定性动画的可靠修复。[E5]

### 10.4 两种复测不能混淆

**渲染器基准：** 固定代码、模板、props、音频、素材、输出设置和运行时。每组明确冷/热缓存状态，重复运行以记录中位数与波动；关闭媒体命中用于测新渲染速度，保留另一组专门测恢复与缓存。

**端到端产品验收：** 用同一口播稿与要求重新制作，允许设计发挥，同时核对动效、美术、素材结合和音画关系。它测产品体验，但不把设计不同造成的耗时差异误归因于底层性能。

不要为了测试并发，每个真实用户任务重新增加必做样片。基准实验在独立的开发验收任务中进行。

### 10.5 本轮不优先动的方向

不先更换 PNG/JPEG、CRF、GPU、分辨率或帧率，不先迁移视频组件，不先共享长期浏览器实例。它们可以影响速度和画质、内存、兼容性，但并不能消除同一任务做两遍；缺少定位数据时改动风险大于确定收益。

输入哈希扫描次数也应单独计时。当前完成分镜后会重新核对冻结输入，可能重复扫描工程和依赖；可以后续依靠可信只读快照和部署版本身份减少扫描，但不能只靠 mtime 或删除核验来放弃运行中输入一致性。[C1]

### 10.6 为什么必须区分渲染速度和创作速度

用同一篇口播重新生成一次视频，模型可能选择不同素材、动作、视觉层次和声音长度。这能测试产品体验，却无法单独解释底层渲染器是否更快。

要判断并发的作用，应固定同一工程、同一音频和同一执行参数。要判断修改后的制作流程是否既快又好，则允许重新创作，但应同时记录新渲染次数、修复类型、缓存失效原因和最终效果。

两类实验得出不同结论都可能合理：底层渲染更快，不代表模型设计耗时更少；端到端更快，也可能只是这次设计更简单。不能将后一种速度改善冒充相同作品的性能优化。

### 10.7 指标需要回答原因，而不是只展示一个总秒数

下一次若仍然耗时较长，记录应能回答：是设计准备增加、实际新生成帧数增加、缓存因什么变化失效，还是同一MP4被重复读取？单看Render总耗时无法区分这些原因。

各并发分镜时间之和也不能代替批次墙钟，渲染和编码阶段可能重叠。资源采样若来自同一个cgroup，不能把多个分镜读到的相同占用相加。指标设计应反映实际观测范围，不填入看似精确但没有测量依据的数字。

这些记录尽量扩展现有progress与timings结构，不新增一套监控服务。先有能够定位本次问题的数据，再决定是否值得优化哈希扫描、解码方式或浏览器启动。

## 11. 一体化修改范围、开发依赖与联合验收

### 11.1 这是一个优化任务，不是多个实施包

本次统一调整制作入口、设计和执行数据、媒体复用、审片材料、交付校验及指标。它们共同服务于同一条正常制作链路，按同一个目标版本在当前选定模板上联测；不再采用字母包，也不规定必须拆成五次上线或要求用户分别确认。

“一起优化”不等于所有文件必须同时写完或只能提交一次代码。开发可以有多个提交和局部测试，但最终要保证工具、模板和 Skill 对同一份数据和流程的理解一致。只修改提示词、只取消一个校验函数、或只排除一个哈希字段，不能作为整套优化已经完成的证明。

### 11.2 保留的是工程依赖，不是新增运行阶段

先统一数据定义：哪些记录解释设计、哪些参数真实决定画面和声音、哪些字段用于审片。渲染派生与输入校验共同使用这一定义，媒体内容键也据此计算。接着让审片材料生成和最终核验使用相同的位置规则，交付入口复用同一次可信检查中的技术结果。

这些改动可以交叉开发，但合入目标版本前必须联合验证；不能让新 Skill 搭配旧试作门槛，也不能让新派生器搭配旧的完整对象相等性检查。具体文件之间的关系见下表。

计时指标应随开发一同补入，正常输入、说明修订、局部内容修改、缓存恢复和最终交付一起验收。并发候选配置通过固定工程测试选择；没有证据支持改善的配置保留原值，不为追求“已优化”而强行提高并发。测量属于本次工作，调参是否启用取决于结果，不变成生产任务的样片要求。

### 11.3 具体修改范围

以下新增文件名是建议；实施时应沿用仓库既有测试组织方式，而不是另建测试框架。

| 涉及职责 | 文件/范围 | 修改内容 |
| --- | --- | --- |
| 正式制作入口 | tools/render_batch.py | 移除强制样片调用；freeze 和 render 前执行可前置检查；保留版本、任务、资源与取消核验 |
| 正式制作入口 | tools/stage_media.py | 拆出资料检查；保留实际媒体和观察检查；不要删除环境 preflight |
| 正式制作入口 | 新增 tools/production_contract.py | 共用设计/执行输入校验、字段投影辅助与取证位置规则；不导入 Agent 逻辑 |
| 正式制作入口 | production-flow.md、video-worker/src/runner/prompts.ts | 全量清理强制样片、重复交付指令，与实际工具一致 |
| 设计与执行数据 | tools/finance_timeline.py、所选模板的类型与执行入口 | 分离设计 sidecar 与实际执行对象，更新派生；拒绝静默吞掉执行字段 |
| 设计与执行数据 | stage_media.fixed_ending_context、相关审核结构 | 共用新投影；同步 design/review 关联；保留固定结束语、片尾和音频合同 |
| 设计与执行数据 | 构建与实际沙箱入口 | 验证并阻止设计/审片记录成为未声明的旁路执行输入；旧模板明确保守模式 |
| 媒体复用 | render_batch.py、stage_media.render_scene | batchVersion 与内容键分开；新批次复用旧有效媒体，记录缓存失效原因 |

发布时需同步工具、模板适配和 Skill 版本，保证 Worker 实际加载的是新版本。对已经冻结的旧任务，不静默把旧 schema 当作新 schema；可以保持旧模式，或在任务内显式迁移并重新核验。缓存 schema 升级初次不命中是正常现象，不能通过手改旧摘要让旧缓存冒充新合同。

### 11.4 发布和旧任务为什么也属于方案的一部分

工具、Skill和模板适配必须形成同一版合同。服务器若仍加载旧提示词或旧模板，代码合并了也不等于任务使用了新流程。

已经冻结的旧任务不能直接改几个哈希标记来冒充新输入契约。可以按旧规则完成或在任务内显式迁移；迁移时重新核对数据、模板兼容性和媒体来源。首次升级缓存schema可能出现冷缓存，这是正常切换成本，不应通过伪造旧摘要掩盖。

本方案不要求立即把所有模板迁成新输入格式。先完成当前目标模板，其他模板保留明确的保守模式；但要在结果与指标中显示模式，防止用户把“仍然整批重做”误判为新方案已经实现却无效。

## 12. 正常制作与变化场景的联合验收

先用完整、无故障的输入验证正常路径：不提交样片，由同一个 Render 完成创作，必要资料随设计和实现形成，正式批量渲染生成当前需要的视频，工具准备已知审片材料，完成审看后通过一次统一交付入口返回结果。记录正常制作耗时、实际新生成内容及重复检查次数。

随后测试说明修订、增加观察位置、用户调整某个独立参数等常见变化，再测试缺项或文件损坏等异常。表中的缺项是测试主动构造的情况，不是要求正常任务先漏写再修复。

| 用例 | 预期行为 |
| --- | --- |
| 完整正常输入，无试作视频 | 同一 Render 连贯完成正式制作、审片及统一交付，不额外请求人工审批 |
| 没有 preflight-review 或样片，其他制作输入完整 | 可以正式批量渲染 |
| 缺少多个设计引用和若干字幕边界错误 | 浏览器渲染前一次返回全部可独立定位问题 |
| 只修 design.description | 不启动新的媒体渲染；重核受影响设计对应关系 |
| 只补 review.observed | 不重渲染、不重新 TTS；不得据此自动放行未解决问题 |
| 只缺动作收束帧证据 | 从有效 MP4 补取，不启动浏览器 |
| 换新 batch ID，真实执行输入完全不变 | 新合同内可复用全部有效分镜 |
| 新输入契约下只改一镜独立标签/参数 | 只重做该镜；它镜内容键不变 |
| 仍依赖完整时间轴的旧模板做局部修改 | 保守失效并明确原因，不假称局部独立 |
| 更换共享样式或字体 | 所有实际受影响镜头失效；第一版可整批保守处理 |
| 延长前镜导致全局进度或 BGM 起点变化 | 正确失效受影响后镜，不复用错误声音 |
| 保持素材路径但修改文件字节 | 内容摘要变化，使相关媒体失效 |
| MP4 或混音损坏 | 拒绝复用；不得只认 marker 中的 passed |
| 在本次交付中修改证据图片 | 图片真实性缓存失效，重新核验或失败 |
| 技术检查规则变化 | 旧检查结果不复用；不因此自动认定旧媒体必须重做 |
| 原始渲染正确，后续封装失败 | 满足原合同的情况下复用原画面和 PCM 恢复 |
| 只改设计意图而画面未改 | 媒体可复用，但相关语义审片需重核；不能继承过期结论 |
| 尝试从组件/构建旁路读取 design/review | 隔离模式拒绝；未支持的模板不能启用非渲染字段排除规则 |
| 批次运行中改正式输入 | 拒绝继续使用过期版本；不伪造新 version 放行 |
| 取消、租约失效、预算耗尽 | 现有任务保护和子进程收敛行为保持有效 |
| 所有检查通过 | 交付整片和全部确认分镜，顺序与原协议一致 |

新增测试不应只 mock 哈希函数。至少用一个包含真实渲染和音轨的固定小工程验证“未命中/命中/局部修改/文件损坏/终检仍有效”的闭环，再用完整 18 镜工程验证耗时和作品质量。小工程用于开发回归，不是重新加回生产任务的强制样片。

### 12.1 为什么正常路径与变化场景都要验证

一次成功只能证明正常路径可用，无法证明本次最关键的错误恢复已经修复。需要主动构造“少一份记录”“补一个观察”“改一个输入”“损坏一个媒体”的差异，分别验证系统是否选择了正确路径。

这些测试的成功标准有两部分：该省的昂贵执行确实没有发生，该保留的错误检查仍然能阻止交付。只看返回completed，可能看不出系统是否重做了18条；只看没有启动浏览器，也可能是错误地跳过所有质量要求。

### 12.2 用历史故障设计一个最重要的回归测试

准备一个已经完成正式分镜、音轨和有效证据的固定任务，保存当前媒体摘要、内容键和执行计数。只补设计说明，不修改任何真实执行参数，再走正常检查与交付路径。

期望结果是：新增浏览器渲染任务数为0，新增渲染帧数为0，不重复收费配音，原有效视频可以继续采用；当前设计关联重新核对。然后把设计预期改为原视频实际没有做到的效果，确认不能因为“媒体可复用”就继承旧通过结论。

这一组正反对照同时证明性能边界与质量边界。它比单独断言“哈希没变”或“耗时降低了”更接近本次要解决的问题。

### 12.3 验收用例需要标明适用契约与实现边界

上表属于同一次整体验收，但不同能力有明确适用前提。当前选定模板应完成配套输入契约后联测；局部独立参数修改只影响一镜，以该模板完成新输入契约为前提。其他尚未隔离全片数据的模板应明确保守失效，不能将它们也计入精确局部复用的完成范围。

“检查规则变更不必重做媒体”也需要区分目标与第一版实现：如果第一版仍对整个stage_media.py做保守工具摘要，修改文件可能导致媒体缓存失效。此时必须如实记录原因；要实现只使检查缓存失效，需进一步按职责拆分相应身份，不能声称已通过这项更强测试。

同样，本次交付内的ValidationContext不承诺跨进程复用。跨进程仍重新验证，不是第一版功能缺陷；它是本方案为降低复杂度保留的明确边界。

<a id="section-13"></a>

## 13. 收益判断与结论边界

按用户历史记录，第二轮批量渲染约 17分36秒，是最明确的待消除重复工作；强制试作约 18分40秒，取消该统一门槛后这段工作结构会改变，但其中部分问题可能在正式产物修订阶段出现。

不能把两项直接相减，承诺下一次一定在某个精确时间内完成。新增设计、美术与实际制作有波动，缓存改造还可能在首次新 schema 运行时产生冷缓存。

整体优化的一项关键行为验收是：**没有试作前置门槛；补一份纯设计/审片说明时，新启动的浏览器渲染数为零，原有效视频不被替换，并且最终关联与质量检查仍能阻止错误交付。**

同一次验收还要证明：正常制作连贯，局部执行输入修订的影响范围正确，当前已知的审片材料由工具准备，同一媒体没有被交付入口重复完整检查。固定工程测试用于判断剩余单轮渲染是否存在更优配置。这些结果共同构成优化结论，不按字母包分别宣告完成。

最后同时比较创作准备时间、实际新渲染次数与帧数、缓存失效原因、取证与终检时间、总体墙钟，以及实际成片的动效、美术、素材结合和音画质量。不能只回到 1.3.0 的时间，就宣称恢复了目标效果。

### 13.1 为什么不把两段时间机械相减当作承诺

消除第二轮整批重渲染，针对的是已观测到的重复工作；取消强制试作，改变的是错误发现和修订的时机。后者可能使部分问题在正式成片后被发现，仍需要实际修复。

此外，下一次设计、素材和音频可能不同，升级后的缓存也可能首次为空。因此历史时间只能帮助确定优先级和构造回归，不能保证下一次完成时间等于“原总耗时减去两个区间”。

### 13.2 最终要优化的不是“检查更少”，而是“每种工作做对一次”

资料在正式制作前检查齐；真正的执行输入变化时只重做应重做的内容；从有效成片提取证据而不重建动画；在可信条件下复用相同技术事实；最终仍核对当前作品、设计、声音与交付关系。

这五点共同成立，才说明改善的是生产流程，而不是用弱化质量要求掩盖耗时。若耗时降低但动画仍像简单文字卡、素材结合退步、音画错误被忽略，就不能称为本轮优化成功。

### 13.3 一句话概括本方案的因果逻辑

**本次慢，不只是因为“要求更多”，而是要求没有落在正确的检查时机和数据边界上；因此先修检查时机、执行输入和恢复范围，再优化剩余渲染性能，保留真正有价值的创作与作品检查。**

## 附录：异常处理与恢复规则，不是正常制作阶段

这里保留开发需要的异常处理细节。它们只在输入缺项、追加观察、文件问题或制作修订时使用，不要求正常任务先出错，也不增加新 Agent 或用户审批。

### 附录.1 “仅记录／证据缺漏”原本指什么

“记录”指设计与实现的对应说明、查看作品后的观察结果等制作资料；“证据”是旧文档对实际 MP4 截图及其来源信息的称呼，本版主线改称“审片材料”。

例如某段视频已经具有所需动画，只是对应设计 ID 未登记，这属于记录问题；视频没有变化，只需再看动作结束位置，可以从该 MP4 提取图片；如果视频确实没做出设计要求的动画，则是实际制作问题，需要修实现。三者不该统一处理成重新渲染。

| 出现的问题 | 首先应该做什么 | 不能混淆成什么 |
| --- | --- | --- |
| 记录或引用不完整 | 补记录，检查与当前作品的关系 | 自动认定原MP4必须重做 |
| 缺少图片或观察 | 从有效MP4取证，真实查看 | 重新启动动画渲染来获得图片 |
| 实际画面、声音或时序错误 | 修实现，再生成受影响内容 | 只改描述或把passed改成true |

这一区分同时影响速度和质量：前两种走轻量恢复，第三种保留真实制作成本。它不是减少检查，而是让每一种错误回到能够修复它的那一层。

“通过”只是检查没有发现阻断项后的正常继续结果，不是要求模型另填一份批准书。“缺漏”是可能的异常结果，不是创作规划中的必经步骤。正常流程不画这两个分支，但程序仍应如实报告错误。

### 附录.2 一次返回全部可独立定位的问题

建议沿用现有 `VISUAL_REVIEW_REQUIRED` 的任务内修复通路，增加结构化类别和 issues，减少 Worker 错误码变更。若另设错误码，必须同时修改 `failure()`、`task_io.py` 的错误投影和预算/无进展处理，不能只在新函数里抛异常。

以下为建议输出结构：

```json
{
  "status": "repair_required",
  "scope": "task_project",
  "error": {
    "code": "VISUAL_REVIEW_REQUIRED",
    "category": "production_input",
    "issues": [
      {
        "sceneId": "scene_007",
        "file": "render/<runId>/design.json",
        "pointer": "/scenes/scene_007/designs",
        "message": "尚未覆盖发言 u021"
      },
      {
        "sceneId": "scene_012",
        "file": "render/<runId>/timeline.json",
        "pointer": "/scenes/11/captions/2/endFrameExclusive",
        "message": "字幕结束位置超出本镜实际帧数"
      }
    ]
  }
}
```

JSON 文件无法解析等根错误仍应优先返回；不要为凑“全量报错”继续执行依赖无效结构的检查。不要通过清空预算账本或无限豁免失败来支持补资料；批量反馈本身应减少无意义的多轮失败。[C7]

### 附录.3 为什么异常时应集中报告问题

设想18条分镜各漏了一项设计引用。如果每次只抛出第一项，Render可能经历“调用—报错—补一项—再次调用”的多轮往返。这里不仅消耗工具时间，还要重复理解错误、定位文件和更新数据，并可能消耗现有修复次数。

更合理的方式是先验证JSON和基本结构；结构有效后，收集所有可以独立判断的问题，一次返回文件、字段位置和原因。修复后再调用同一入口。这样减少的是无信息增量的往返，不是让错误无限重试。

对依赖无效数据的后续检查不能强行继续。例如时间轴无法解析时，不应臆造“第12镜字幕越界”；应先报告根错误。预算、取消、授权及连续无进展保护仍沿用现有机制，不因新增检查就另开一套宽松恢复规则。[C7]

### 附录.4 修改范围与质量结论仍分别核对

只是移动异常说明的位置，不删除恢复能力或质量要求。说明文字变了，媒体未必需要重新生成，但当前设计预期与作品的关系要重新核对；真正影响画面、声音或时序的输入变了，必须正确失效相关媒体；补截图从有效视频提取，不能填一个“已查看”来替代实际观察。

这些规则的目的，是在发生变化时准确处理影响范围，不是把整套正常制作改成持续修补程序。它们和正常制作、媒体复用、统一交付一起开发并联合验证。
